# TaskFlow: บทพูดล้วน 19 สไลด์

ฉบับสำหรับผู้ชาย อ่านตามลำดับชุดรวม 19 หน้า คำศัพท์และคำตอบคำถามอยู่ในไฟล์คู่มือฉบับเต็ม เลขในวงเล็บช่วยเทียบกับ PDF เดิมหรือไฟล์สไลด์ทดแทน 13 หน้า

## สไลด์ 01: TaskFlow: ระบบจัดการงานส่วนตัว

(PDF เดิม หน้า 01)

ผมจะนำเสนอ TaskFlow เว็บจัดการงานส่วนตัว ตั้งแต่หน้าจอที่ผู้ใช้กด ไปจนถึงข้อมูลที่เก็บในฐานข้อมูลครับ หน้าจอใช้ React และ Tailwind ส่วน Hono รับคำขอและตรวจสิทธิ์ ก่อนทำงานกับ SQLite เว็บใช้ JWT ร่วมกับ session เพื่อรู้ว่าใครกำลังใช้งาน ส่วน API key ให้ n8n เชื่อมต่อการแจ้งเตือน ทั้งสองอย่างมีหน้าที่ต่างกัน มีลิงก์ตั้งรหัสผ่านใหม่ทางอีเมล เป้าหมายของงานนี้คืออธิบายให้ได้ว่า ข้อมูลผ่านแต่ละส่วนอย่างไร และทำไมผู้ใช้จึงจัดการได้เฉพาะงานของตัวเอง

## สไลด์ 02: ปัญหาและขอบเขตของระบบ

(PDF เดิม หน้า 02)

ขอบเขตของ TaskFlow คือช่วยเก็บงานให้อยู่ในที่เดียวครับ ผู้ใช้เข้าสู่ระบบ เพิ่มชื่อกับรายละเอียด แล้วเลือกสถานะ ความสำคัญ และวันครบกำหนดได้ งานเป็นของบัญชีที่สร้าง ไม่ใช่งานร่วมทีม เบื้องหลังมีการตรวจรหัสผ่านและเจ้าของข้อมูล ส่วน n8n เป็นทางเลือกสำหรับแจ้งเตือน ไม่ต้องเปิดก็จัดการงานบนเว็บได้ เราใช้ monorepo คือเก็บหน้าเว็บ ส่วน API และกติกาข้อมูลไว้ในที่เดียว เพื่อให้แก้ข้อมูลที่ใช้ร่วมกันได้ตรงกัน โดยไม่เพิ่มระบบที่เกินขอบเขตของงานนี้

## สไลด์ 03: หน้าจอจริงและเส้นทางการใช้งาน

(ไฟล์สไลด์ทดแทน หน้า 01)

หน้านี้เป็นภาพระบบที่รันจริงด้วยข้อมูลตัวอย่างครับ ด้านบนสรุปจำนวนงานตามสถานะ ด้านล่างเป็นรายการที่ค้นหาหรือกรองได้ ผู้ใช้เพิ่มงาน กำหนดวัน และแก้สถานะจากรายการได้ ตัวเลขบนภาพเป็นข้อมูลของบัญชีเดโม ไม่ใช่ผลวัดผู้ใช้จริง สิ่งสำคัญคือหน้าจอแสดงเฉพาะข้อมูลที่ backend อนุญาต การซ่อนรายการบนจออย่างเดียวไม่พอ ทุกคำขออ่านหรือแก้งานยังต้องตรวจเจ้าของที่ backend อีกครั้ง ถ้ารู้หมายเลขงานของคนอื่น ก็ไม่ได้แปลว่าจะเปิดหรือแก้งานนั้นได้

## สไลด์ 04: สถาปัตยกรรมของ TaskFlow

(ไฟล์สไลด์ทดแทน หน้า 02)

เส้นทางหลักเริ่มจากเบราว์เซอร์ ส่งคำขอไป Hono แล้วอ่านหรือบันทึกข้อมูลใน SQLite ครับ ตอนพัฒนา Vite เปิดหน้าเว็บที่ 5173 และส่งคำขอ API ต่อไปที่ 3000 หลังสร้างไฟล์เว็บแล้ว Hono เสิร์ฟเว็บกับ API จากที่อยู่เดียวกันได้ ส่วนอีเมลมีสองทางที่ต้องแยกให้ชัด ลิงก์ตั้งรหัสผ่านใหม่ส่งจาก backend ผ่าน Gmail SMTP โดยตรง ขณะที่ n8n ใช้ API key อ่านงานเพื่อแจ้งเตือนตามเวลา การตั้งอีเมลของ backend จึงไม่ได้ตั้งการเชื่อมต่อให้ n8n ไปด้วย

## สไลด์ 05: Monorepo และ package ที่แชร์ร่วมกัน

(ไฟล์สไลด์ทดแทน หน้า 03)

โครงสร้างนี้แยกส่วนตามหน้าที่แต่เก็บในโปรเจกต์เดียวครับ apps/web เป็นหน้าจอ apps/api รับคำขอและคุยฐานข้อมูล packages/shared เก็บชนิดข้อมูลและกติกาที่ใช้ร่วมกัน workflow อยู่ใน n8n และคู่มืออยู่ใน docs root มีคำสั่งตรวจชนิดข้อมูล ทดสอบ และสร้างไฟล์เว็บ ส่วนคำสั่ง dev ใช้ concurrently เปิด Vite กับ Hono คู่กัน จุดนี้เป็นหน้าที่ของ script ไม่ใช่คุณสมบัติพิเศษของ monorepo ตัว monorepo ช่วยจัดโค้ด ส่วน npm workspaces ช่วยเชื่อมแพ็กเกจครับ

## สไลด์ 06: Shared schema และการตรวจข้อมูล

(PDF เดิม หน้า 05)

หน้านี้แสดงว่าทำไมต้องตรวจข้อมูลทั้งสองฝั่งครับ หน้าเว็บตรวจฟอร์มเพื่อบอกผู้ใช้ทันที เช่น ชื่องานสั้นเกินไป ส่วน API ตรวจซ้ำ เพราะคนเรียกอาจส่งคำขอเองโดยไม่ผ่านหน้าเว็บ ทั้งสองฝั่งใช้กติกาจาก shared ร่วมกัน ถ้าขอแก้งานแต่ส่งสถานะที่ไม่ยอมรับ API จะตอบ 400 และไม่เขียนข้อมูลงาน คำว่าไม่แตะ SQL บนสไลด์จึงต้องเข้าใจว่าไม่บันทึกข้อมูลผิด ไม่ได้หมายความว่าไม่มีการอ่านฐานข้อมูลเลย เพราะขั้นตรวจ session อาจอ่าน SQL ก่อนถึงการตรวจฟอร์ม

## สไลด์ 07: ER diagram ของฐานข้อมูล

(PDF เดิม หน้า 06)

หน้านี้เป็นแผนผังฐานข้อมูลของ TaskFlow ครับ ผู้ใช้หนึ่งคนมีงาน เซสชัน และคีย์แจ้งเตือนได้หลายรายการ เราแยกข้อมูลเป็นหกตาราง เพราะมีหน้าที่และอายุต่างกัน ทุกตารางมีไอดีระบุแต่ละแถว ส่วนฟอเรนคีย์เชื่อมว่าแถวนั้นเกี่ยวข้องกับผู้ใช้หรืองานใด ตารางล่างเก็บประวัติแจ้งเตือน โดยห้ามบันทึกชุดเจ้าของ งาน วัน และช่องทางเดิมซ้ำ แต่ความสัมพันธ์ในฐานข้อมูลยังไม่ได้อนุญาตให้เปิดดูงาน ฝั่ง API ต้องตรวจเจ้าของด้วย ซึ่งผมจะอธิบายในหน้าถัดไป

## สไลด์ 08: SQL ที่ตรวจเจ้าของงานจริง

(ไฟล์สไลด์ทดแทน หน้า 04)

หน้านี้แสดงการตรวจเจ้าของงานจริง เราค้นหาทั้งไอดีงานและไอดีเจ้าของที่ต้องตรงกับผู้เข้าสู่ระบบ ไอดีงานมาจากคำขอ ส่วนไอดีผู้ใช้มาจากเซสชันที่เซิร์ฟเวอร์ตรวจแล้ว ไม่ให้ผู้เรียกกำหนดเจ้าของเอง เครื่องหมายคำถามเป็นช่องรับค่าผ่านพารามิเตอร์ ซึ่งแยกข้อมูลออกจากคำสั่ง SQL ถ้างานไม่มีหรือเป็นของคนอื่น ระบบตอบไม่พบเหมือนกัน การแก้ไขและลบงานใช้หลักเดียวกัน หัวใจคือรู้รหัสงานอย่างเดียว ยังเข้าถึงงานของผู้อื่นไม่ได้ครับ

## สไลด์ 09: JWT, cookie และการเพิกถอน session

(ไฟล์สไลด์ทดแทน หน้า 05)

เมื่อเข้าสู่ระบบ เบราว์เซอร์ได้รับ JWT ผ่านคุกกี้ ภายในมีรหัสผู้ใช้ รหัสเซสชัน และเวลาหมดอายุ ข้อมูลอ่านได้ จึงไม่ใส่ความลับ ทุกคำขอที่เปิดงาน เซิร์ฟเวอร์ตรวจลายเซ็น ผู้ออกโทเคน ผู้รับ และเวลาหมดอายุ แล้วตรวจเซสชันในฐานข้อมูลว่ายังไม่หมดอายุและไม่ถูกยกเลิก เมื่อออกจากระบบ เราลบคุกกี้และยกเลิกเซสชัน ทำให้สำเนาโทเคนเดิมใช้ต่อไม่ได้ อายุเซสชันคือสามสิบนาที ยังไม่มีรีเฟรชโทเคนสำหรับต่ออายุ ถ้าหมดอายุ ผู้ใช้ต้องเข้าสู่ระบบใหม่ครับ

## สไลด์ 10: JWT, API key และ reset token

(ไฟล์สไลด์ทดแทน หน้า 06)

หลักฐานสามชนิดมีหน้าที่ต่างกัน JWT ใช้กับผู้ใช้เว็บ API key ให้ n8n เรียกงานแจ้งเตือน ส่วน reset token ใช้เฉพาะตั้งรหัสผ่านใหม่ อายุจึงต่างกัน ฐานข้อมูลเก็บแฮชของคีย์และลิงก์แทนค่าดิบ ส่วนรหัสผ่านใช้เอสคริปต์ร่วมกับซอลต์ เพราะรหัสที่คนตั้งอาจเดาง่ายกว่าโทเคนสุ่ม แฮชไม่ใช่การเข้ารหัสที่มีคีย์ถอดกลับ เมื่อรีเซ็ตสำเร็จ ระบบยกเลิกทุกเซสชันและลิงก์รีเซ็ตที่ค้าง แต่ API key ต้องยกเลิกแยกครับ

## สไลด์ 11: ลำดับการขอลิงก์และตั้งรหัสผ่านใหม่

(PDF เดิม หน้า 09)

อ่านแผนภาพจากบนลงล่าง ผู้ใช้ส่งอีเมลขอลิงก์ หากมีบัญชีและยังขอได้ ระบบสุ่มโทเคน เก็บแฮชกับเวลาหมดอายุ แล้วตอบข้อความกลางก่อนส่งเมล ข้อความที่เหมือนกันช่วยไม่เปิดเผยว่าอีเมลใดมีบัญชี ผู้ใช้เปิดลิงก์แล้วส่งโทเคนพร้อมรหัสใหม่ให้ API ตรวจ เลขสองศูนย์สองแปลว่ารับคำขอ ไม่ได้ยืนยันว่าเมลถึงแล้ว หลักฐานปัจจุบันทดสอบตัวรับ SMTP ในเครื่อง ยังไม่ใช่ Gmail จริง และ n8n ไม่ได้ส่งลิงก์รีเซ็ตนี้ครับ

## สไลด์ 12: Token ใช้ครั้งเดียวและ transaction

(ไฟล์สไลด์ทดแทน หน้า 07)

ระบบคำนวณแฮชรหัสใหม่ก่อนเริ่มทรานแซกชัน เพื่อไม่ล็อกฐานข้อมูลระหว่างคำนวณ จากนั้นยืนยันสิทธิ์ใช้โทเคนอีกครั้ง ถ้ายังไม่ใช้และไม่หมดอายุจึงเปลี่ยนรหัส ยกเลิกเซสชัน และปิดลิงก์รีเซ็ตที่ค้าง ทุกขั้นต้องสำเร็จพร้อมกัน ถ้าผิดพลาดจะย้อนกลับทั้งชุด แม้สองคำขอใช้ลิงก์เดียวกันพร้อมกัน ก็สำเร็จได้เพียงหนึ่งคำขอ ส่วนล็อกอินที่กำลังตรวจรหัสเดิมขณะรีเซ็ต ต้องอ่านแฮชล่าสุดก่อนออกเซสชัน สุดท้ายให้ผู้ใช้เข้าสู่ระบบใหม่เองครับ

## สไลด์ 13: หน้าตั้งรหัสผ่านใหม่ที่รันจริง

(ไฟล์สไลด์ทดแทน หน้า 08)

หน้านี้คือหน้าตั้งรหัสผ่านใหม่ที่รันจริงครับ ผู้ใช้เปิดลิงก์อีเมล แล้วกรอกรหัสใหม่ 12 ถึง 128 ตัวอักษร พร้อมยืนยันให้ตรงกัน หน้าเว็บอ่าน token เข้า memory แล้วลบออกจากแถบที่อยู่ทันที เพื่อลดการทิ้งลิงก์ที่มีสิทธิ์เปลี่ยนรหัสไว้ ถ้า refresh ค่าใน memory จะหาย จึงต้องเปิดลิงก์ต้นฉบับจากอีเมลอีกครั้ง โดยลิงก์ต้องยังไม่หมดอายุและไม่ถูกใช้ เมื่อบันทึกสำเร็จ ระบบยกเลิก session เดิมทุกอัน แล้วให้ผู้ใช้เข้าสู่ระบบใหม่ด้วยรหัสใหม่

## สไลด์ 14: ตั้ง Gmail SMTP และขอบเขตหลักฐาน

(ไฟล์สไลด์ทดแทน หน้า 09)

การส่งอีเมลตั้งรหัสใหม่ทำจาก backend ไม่ต้องเปิด n8n ครับ เริ่มจาก setup เพื่อเติมค่าที่ขาด แล้วใส่ Gmail App Password ในเครื่อง ตั้ง APP_PUBLIC_URL ให้ผู้รับเปิดถึง คำสั่ง mail:check ตรวจการเชื่อมต่อและยืนยันตัวตน แต่ไม่ส่งอีเมล สิ่งที่ผ่านแล้วคือ SMTP receiver ในเครื่อง ยังไม่มีหลักฐาน Gmail ถึง inbox การส่งเป็น async ใน process เดียว ไม่มีคิวถาวร ถ้าโปรแกรมหยุดอาจต้องขอลิงก์ใหม่ และ SMTP ยอมรับข้อความก็ยังไม่ยืนยันว่าเข้ากล่องรับ

## สไลด์ 15: การตรวจ request ก่อนแตะข้อมูล

(ไฟล์สไลด์ทดแทน หน้า 10)

คำขอต้องผ่านหลายด่านก่อนแตะข้อมูลครับ ระบบใส่ request_id และ secure headers จำกัด body 16 KB และตรวจ Origin จากนั้นเลือก credential ตาม route งานส่วนตัวใช้ session ส่วน integrations ใช้ API key ข้อมูลต้องเป็น JSON และผ่าน Zod ก่อนทำ SQL ซึ่งต้องตรวจเจ้าของอีกชั้น ระบบจำกัด login กับ register รวม 20 ครั้งต่อ IP ใน 15 นาที ส่วน forgot-password 5 และ reset-password 10 ครั้ง ถ้าผิดพลาดจะคืน code ข้อความ และ request_id เพื่อค้นหาคำขอนั้น

## สไลด์ 16: สิทธิ์และสถานะของงาน

(ไฟล์สไลด์ทดแทน หน้า 11)

ตารางนี้เทียบสิทธิ์เมื่อใช้ credential เพียงชนิดเดียวครับ Session จัดการงานและ key ของตัวเองได้ ส่วน key reminders ใช้อ่านงานถึงกำหนดและบันทึกผลแจ้งเตือนของเจ้าของ key จึงนำไปเพิ่มหรือแก้งานไม่ได้ Session อย่างเดียวก็เข้า integration ไม่ได้ ถ้าส่งทั้งสองชนิด integration ใช้เจ้าของ key เป็นตัวตน ด้านล่างคือ pending ยังไม่เริ่ม in_progress กำลังทำ และ completed เสร็จแล้ว เจ้าของเปลี่ยนสถานะได้โดยไม่บังคับลำดับ การแยกสิทธิ์ช่วยให้โปรแกรมภายนอกทำได้เท่าที่จำเป็น

## สไลด์ 17: API routes และข้อผิดพลาด

(ไฟล์สไลด์ทดแทน หน้า 12)

ทุก path หน้านี้ต้องเติม /api ด้านหน้าครับ ต้องอ่าน method คู่กับ path: GET อ่าน POST สร้างหรือสั่งทำงาน PATCH แก้บางส่วน และ DELETE ลบ รายการงานกับงานที่มี id ใช้ method ต่างกัน Reset-password รับ token กับ password ไม่ได้คืน token ใหม่ และไม่ต้องมี session ส่วน error ใช้แยกสาเหตุ เช่น 401 credential ใช้ไม่ได้ 403 Origin ถูกปฏิเสธ และ 429 เรียกถี่เกิน สำหรับ 503 หมายถึงยังไม่ตั้ง SMTP ไม่ใช่ส่งเมลล้มเหลวหลังตอบ 202

## สไลด์ 18: n8n workflow แจ้งเตือนรายวัน

(PDF เดิม หน้า 16)

เวลาเจ็ดโมงครึ่งตาม Bangkok ตัว Schedule เริ่ม workflow แล้วใช้ API key ของบัญชีหนึ่งอ่านงานถึงกำหนดครับ ถ้าไม่มีงานก็จบ ถ้ามีจึงส่งอีเมลผ่าน SMTP แล้วบันทึกผลผ่าน API บันทึกนี้ช่วยลดการส่งซ้ำในวันเดิม แต่ SMTP กับ SQL ไม่ใช่ธุรกรรมเดียวกัน ถ้าส่งแล้วหยุดก่อนบันทึก การรันซ้ำอาจส่งอีก จึงควรใช้ workflow ชุดเดียวและเลี่ยงการรันพร้อมกัน ตอนนี้ไฟล์และ expression ผ่าน static validation แล้ว ยังไม่ได้รัน n8n ส่งเมลจริง

## สไลด์ 19: หลักฐานการทดสอบที่รันจริง

(ไฟล์สไลด์ทดแทน หน้า 13)

ผลที่บันทึกไว้คือ functional tests ผ่าน 54 จาก 54 ครับ แบ่งเป็น 35 เดิม 17 reset และ 2 mail ซึ่งคือ config หนึ่งกรณี กับ local SMTP end-to-end อีกหนึ่ง ครอบคลุมเจ้าของข้อมูล token หมดอายุและใช้ครั้งเดียว การยกเลิก session และ login ที่ชนกับ reset ส่วน build และหน้าจอหลายความกว้างผ่านแล้ว แต่ยังไม่มี load test หรือหลักฐาน Gmail ถึง inbox และ n8n ส่งจริง จึงต้องตรวจส่วนเหล่านี้ต่อก่อนใช้งานจริง
