ฉบับสำหรับผู้ชาย ใช้ “ผม” และ “ครับ” ตามจังหวะ เนื้อหาบทพูดแยกจากตารางคำศัพท์ ไม่จำเป็นต้องอ่านตารางทั้งหมดบนเวที

**ลำดับนี้เป็นชุดรวม 19 หน้า** จาก PDF เดิม 16 หน้า เมื่อใช้หน้าทดแทน 10 หน้าและแทรกหน้าเสริม 3 หน้า เลข “สไลด์” ในคู่มือนี้จึงต่างจากเลขในไฟล์ทดแทน 13 หน้า แต่ระบุจุดอ้างอิงไว้ทุกหน้า

## สไลด์ 01: TaskFlow: ระบบจัดการงานส่วนตัว

**ที่มา:** PDF เดิม หน้า 01 — หน้าปก

### บทพูด

ผมจะนำเสนอ TaskFlow เว็บจัดการงานส่วนตัว ตั้งแต่หน้าจอที่ผู้ใช้กด ไปจนถึงข้อมูลที่เก็บในฐานข้อมูลครับ หน้าจอใช้ React และ Tailwind ส่วน Hono รับคำขอและตรวจสิทธิ์ ก่อนทำงานกับ SQLite เว็บใช้ JWT ร่วมกับ session เพื่อรู้ว่าใครกำลังใช้งาน ส่วน API key ให้ n8n เชื่อมต่อการแจ้งเตือน ทั้งสองอย่างมีหน้าที่ต่างกัน มีลิงก์ตั้งรหัสผ่านใหม่ทางอีเมล เป้าหมายของงานนี้คืออธิบายให้ได้ว่า ข้อมูลผ่านแต่ละส่วนอย่างไร และทำไมผู้ใช้จึงจัดการได้เฉพาะงานของตัวเอง

### ศัพท์ที่ต้องรู้

| คำบนสไลด์ | ความหมายแบบง่าย | ใช้ทำอะไรใน TaskFlow |
| --- | --- | --- |
| Technical Review — เทคนิเคิล รีวิว | การตรวจและอธิบายการออกแบบกับโค้ด ว่าทำงานอย่างไรและมีข้อจำกัดอะไร | ชี้จากหน้าจอไปยังคำขอ การตรวจสิทธิ์ และข้อมูลที่บันทึกจริง |
| TaskFlow — ทาสก์โฟลว์ | ชื่อโปรเจกต์ ไม่ใช่ชื่อเครื่องมือหรือมาตรฐาน | เว็บเก็บและติดตามงานส่วนตัว |
| React — รีแอ็กต์ | ชุดเครื่องมือสร้างหน้าจอจากส่วนย่อยที่นำกลับมาใช้ได้ | สร้างฟอร์ม รายการงาน และหน้าต่างเข้าสู่ระบบ |
| Tailwind CSS — เทลวินด์ ซีเอสเอส | เครื่องมือจัดหน้าตาด้วยชื่อรูปแบบสำเร็จ เช่น ระยะห่าง สี และการเรียงช่อง | ทำหน้าจอให้สม่ำเสมอและปรับตามขนาดจอ |
| CSS — ซีเอสเอส; Cascading Style Sheets | ภาษากำหนดหน้าตาเว็บ เช่น สี ตัวอักษร และตำแหน่ง | กำหนดธีมและรูปแบบที่ใช้ร่วมกันทั้งเว็บ |
| Hono — โฮโน | ชุดเครื่องมือช่วยสร้างส่วนที่รับและตอบคำขอผ่านเว็บ | รับคำขอเข้าสู่ระบบ จัดการงาน และเชื่อมต่อโปรแกรมอื่น |
| SQLite — เอสคิวไลต์ | โปรแกรมฐานข้อมูลที่เก็บข้อมูลเป็นไฟล์ ไม่ต้องเปิดบริการฐานข้อมูลแยกอีกตัว | เก็บผู้ใช้ งาน session คีย์ ลิงก์ตั้งรหัสใหม่ และประวัติแจ้งเตือน |
| Frontend — ฟรอนต์เอนด์ | ส่วนหน้าจอที่ทำงานในโปรแกรมเปิดเว็บและรับการกดของผู้ใช้ | แสดงข้อมูลและส่งสิ่งที่กรอกไปให้ระบบตรวจ |
| SQL — เอสคิวแอล; Structured Query Language | ภาษาสำหรับอ่าน เพิ่ม แก้ไข และลบข้อมูลในฐานข้อมูลแบบตาราง | อ่านและบันทึกข้อมูลใน SQLite |
| JWT — เจดับเบิลยูที; JSON Web Token | รูปแบบข้อมูลที่มีลายเซ็นให้ตรวจว่าไม่ถูกแก้ไข เนื้อหาอ่านได้ จึงไม่ใส่รหัสผ่าน | แนบเลขอ้างอิงผู้ใช้และ session ให้ฝั่งรับคำขอตรวจ |
| Session — เซสชัน | ช่วงการเข้าสู่ระบบที่ระบบบันทึกสถานะไว้ และสั่งยกเลิกได้ | SQL เก็บ session เพื่อให้ออกจากระบบแล้วปฏิเสธการใช้ JWT เดิมต่อได้ |
| API — เอพีไอ; Application Programming Interface | จุดรับส่งคำขอที่โปรแกรมตกลงรูปแบบไว้ | ให้หน้าจอและ n8n ขอให้ backend ทำงาน |
| API key — เอพีไอคีย์ | ค่าลับที่ระบบออกให้โปรแกรมอื่นใช้ยืนยันการเชื่อมต่อ | ให้ n8n อ่านงานเตือนและบันทึกผล เฉพาะบัญชีเจ้าของคีย์ |
| n8n — เอ็นเอทเอ็น | โปรแกรมเรียงขั้นตอนอัตโนมัติ เช่น ตั้งเวลา อ่านข้อมูล แล้วส่งอีเมล | เป็นส่วนเสริมสำหรับแจ้งงานครบกำหนด ไม่ใช่ผู้ส่งอีเมลตั้งรหัสผ่านใหม่ |
| ลิงก์ตั้งรหัสผ่านใหม่ | ที่อยู่เว็บพร้อมค่าลับชั่วคราว สำหรับผู้ที่ลืมรหัสผ่าน | ให้ผู้รับอีเมลตั้งรหัสใหม่ภายใน 15 นาที และใช้สำเร็จได้ครั้งเดียว |
| `+`, `/`, `•` | เครื่องหมายรวมรายการหรือแบ่งหัวข้อในหน้าปก ไม่ใช่การบวกหรือหารข้อมูล | ช่วยอ่านชื่อเครื่องมือและหัวข้อที่นำเสนอ |

### คำถามที่อาจถูกถาม

**ถาม 1: ทำไมต้องมีทั้ง JWT และ API key?**  
ตอบ: JWT ร่วมกับ session ใช้กับคนที่เข้าสู่เว็บ ส่วน API key ใช้กับโปรแกรมแจ้งเตือน และได้สิทธิ์เฉพาะทาง จึงไม่ต้องให้ n8n ถือรหัสผ่านของผู้ใช้ครับ

**ถาม 2: ชื่อวิดีโอมีคำว่า Production Ready แปลว่างานนี้พร้อมใช้งานจริงทุกด้านหรือไม่?**  
ตอบ: ยังสรุปเช่นนั้นไม่ได้ครับ งานนี้รันและตรวจพฤติกรรมได้ แต่การทดสอบโหลด การดูแลระบบจริง และการส่ง Gmail ถึงผู้รับยังเป็นคนละขอบเขตกับผลทดสอบในเครื่อง

**ใจความจำ:** หน้าจอรับความต้องการ แต่ backend เป็นผู้ตรวจตัวตน สิทธิ์ และข้อมูลก่อนบันทึก

## สไลด์ 02: ปัญหาและขอบเขตของระบบ

**ที่มา:** PDF เดิม หน้า 02

### บทพูด

ขอบเขตของ TaskFlow คือช่วยเก็บงานให้อยู่ในที่เดียวครับ ผู้ใช้เข้าสู่ระบบ เพิ่มชื่อกับรายละเอียด แล้วเลือกสถานะ ความสำคัญ และวันครบกำหนดได้ งานเป็นของบัญชีที่สร้าง ไม่ใช่งานร่วมทีม เบื้องหลังมีการตรวจรหัสผ่านและเจ้าของข้อมูล ส่วน n8n เป็นทางเลือกสำหรับแจ้งเตือน ไม่ต้องเปิดก็จัดการงานบนเว็บได้ เราใช้ monorepo คือเก็บหน้าเว็บ ส่วน API และกติกาข้อมูลไว้ในที่เดียว เพื่อให้แก้ข้อมูลที่ใช้ร่วมกันได้ตรงกัน โดยไม่เพิ่มระบบที่เกินขอบเขตของงานนี้

| API keys | ค่าลับสำหรับโปรแกรมที่เชื่อมต่อ แต่ละคีย์มีเจ้าของและเงื่อนไขการใช้ | แยกการแจ้งเตือนของ n8n ออกจากการเข้าสู่เว็บ |

| Integration — อินทิเกรชัน | การให้โปรแกรมคนละตัวทำงานร่วมกันผ่านช่องทางที่กำหนด | n8n เรียก API เพื่ออ่านงานและบันทึกประวัติเตือน |
| n8n | โปรแกรมจัดลำดับงานอัตโนมัติ | ช่วยส่งอีเมลเตือน เป็นส่วนเสริมของระบบงานส่วนตัว |
| Monorepo — โมโนรีโป | เก็บหลายแอปหรือชุดโค้ดที่เกี่ยวข้องในแหล่งเก็บโค้ดเดียว | รวม web, api และ shared ไว้ใน TaskFlow |
| React | ชุดเครื่องมือสร้างและปรับหน้าจอตามข้อมูล | รับการกรอกและแสดงงานของผู้ใช้ |
| Repository — รีพอซิทอรี | แหล่งเก็บไฟล์โค้ดและประวัติการเปลี่ยนแปลง | ที่เก็บโปรเจกต์ TaskFlow ทั้งชุด |
| Schema — สคีมา | กติกาว่าข้อมูลต้องมีช่องอะไรและค่าแบบไหนจึงผ่าน | กำหนดความยาวชื่องาน วันที่ สถานะ และความสำคัญ |

| Package — แพ็กเกจ | ชุดโค้ดที่ตั้งชื่อและประกาศสิ่งที่ต้องใช้ไว้ | shared เป็นแพ็กเกจกติกาที่เว็บและ API เรียกใช้ |
| npm — เอ็นพีเอ็ม | เครื่องมือติดตั้งและจัดการชุดโค้ดของภาษา JavaScript | ติดตั้งเครื่องมือและเรียกคำสั่งของโปรเจกต์ |
| Workspaces — เวิร์กสเปซ | ความสามารถของ npm ที่เชื่อมแพ็กเกจภายในโปรเจกต์เดียวกัน | ทำให้เว็บกับ API ใช้ `@taskflow/shared` ได้ |
| `POST /api/tasks` ในตัวอย่าง | `POST` คือส่งข้อมูลเพื่อสร้างรายการ; `/api/tasks` คือที่อยู่ของจุดรับคำขอ | สร้างงานใหม่ โดย backend ใช้เจ้าของจาก session ไม่รับเจ้าของที่กรอกมาเอง |

### คำถามที่อาจถูกถาม

**ถาม 1: ถ้าไม่เปิด n8n ระบบยังทำอะไรได้?**  
ตอบ: ยังสมัคร เข้าสู่ระบบ จัดการงาน และใช้การตั้งรหัสผ่านใหม่ได้เมื่อ backend ตั้ง SMTP แล้วครับ ส่วน n8n มีไว้แจ้งงานครบกำหนดตามเวลาเท่านั้น

**ถาม 2: งานความสำคัญสูงทำให้มีสิทธิ์พิเศษหรือไม่?**  
ตอบ: ไม่ครับ ความสำคัญเป็นแค่ข้อมูลช่วยจัดงาน สิทธิ์ยังมาจากผู้ใช้ที่ตรวจแล้วและเจ้าของงาน ไม่ได้มาจากป้ายความสำคัญ

**ใจความจำ:** งานนี้เป็นงานส่วนตัวของแต่ละบัญชี ส่วนการแจ้งเตือนเป็นทางเลือกเพิ่มเติม

## สไลด์ 03: หน้าจอจริงและเส้นทางการใช้งาน

### บทพูด

หน้านี้เป็นภาพระบบที่รันจริงด้วยข้อมูลตัวอย่างครับ ด้านบนสรุปจำนวนงานตามสถานะ ด้านล่างเป็นรายการที่ค้นหาหรือกรองได้ ผู้ใช้เพิ่มงาน กำหนดวัน และแก้สถานะจากรายการได้ ตัวเลขบนภาพเป็นข้อมูลของบัญชีเดโม ไม่ใช่ผลวัดผู้ใช้จริง สิ่งสำคัญคือหน้าจอแสดงเฉพาะข้อมูลที่ backend อนุญาต การซ่อนรายการบนจออย่างเดียวไม่พอ ทุกคำขออ่านหรือแก้งานยังต้องตรวจเจ้าของที่ backend อีกครั้ง ถ้ารู้หมายเลขงานของคนอื่น ก็ไม่ได้แปลว่าจะเปิดหรือแก้งานนั้นได้

### คำถามที่อาจถูกถาม

**ถาม 1: ตัวเลข 5 งานบนภาพหมายความว่าอย่างไร?**  
ตอบ: คือจำนวนงานในบัญชีตัวอย่างตอนจับภาพครับ ไม่ใช่จำนวนผู้ใช้ ไม่ใช่ข้อมูลคงที่ และไม่ใช่ผลทดสอบประสิทธิภาพ

**ถาม 2: ถ้าแก้ที่อยู่คำขอเป็นหมายเลขงานของคนอื่นจะเกิดอะไรขึ้น?**  
ตอบ: เมื่อส่งด้วย session ของเรา backend จะหาโดยใช้ทั้งหมายเลขงานและเจ้าของจาก session ถ้าเจ้าของไม่ตรงจะคืน 404 เช่นเดียวกับไม่พบงานครับ

**ใจความจำ:** หน้าจอช่วยให้ใช้งานง่าย แต่สิทธิ์ของข้อมูลต้องตรวจซ้ำที่ backend ทุกครั้ง

## สไลด์ 04: สถาปัตยกรรมของ TaskFlow

**ที่มา:** สไลด์ทดแทน 02 — แทน PDF เดิม หน้า 03

### บทพูด

เส้นทางหลักเริ่มจากเบราว์เซอร์ ส่งคำขอไป Hono แล้วอ่านหรือบันทึกข้อมูลใน SQLite ครับ ตอนพัฒนา Vite เปิดหน้าเว็บที่ 5173 และส่งคำขอ API ต่อไปที่ 3000 หลังสร้างไฟล์เว็บแล้ว Hono เสิร์ฟเว็บกับ API จากที่อยู่เดียวกันได้ ส่วนอีเมลมีสองทางที่ต้องแยกให้ชัด ลิงก์ตั้งรหัสผ่านใหม่ส่งจาก backend ผ่าน Gmail SMTP โดยตรง ขณะที่ n8n ใช้ API key อ่านงานเพื่อแจ้งเตือนตามเวลา การตั้งอีเมลของ backend จึงไม่ได้ตั้งการเชื่อมต่อให้ n8n ไปด้วย

### คำถามที่อาจถูกถาม

**ถาม 1: SQLite มี 6 ตารางอะไรบ้าง?**  
ตอบ: `users` เก็บผู้ใช้, `auth_sessions` เก็บการเข้าสู่ระบบ, `password_reset_tokens` เก็บข้อมูลตรวจลิงก์ตั้งรหัสใหม่, `tasks` เก็บงาน, `api_keys` เก็บข้อมูลคีย์ และ `reminder_deliveries` เก็บประวัติแจ้งเตือนครับ

**ถาม 2: ตั้ง Gmail ของ backend แล้ว n8n ส่งเมลได้ทันทีหรือไม่?**  
ตอบ: ยังไม่ได้ครับ n8n ต้องตั้งการเชื่อมต่อ API key กับบริการส่งอีเมลของตัวเอง และเปิดขั้นตอนแจ้งเตือน ทั้งสองส่วนใช้การตั้งค่าคนละที่

**ใจความจำ:** เว็บคุยกับ API แล้ว API คุยกับฐานข้อมูล ส่วนอีเมลกู้บัญชีกับอีเมลเตือนงานเป็นคนละเส้นทาง

## สไลด์ 05: Monorepo และ package ที่แชร์ร่วมกัน

**ที่มา:** สไลด์ทดแทน 03 — แทน PDF เดิม หน้า 04

### บทพูด

โครงสร้างนี้แยกส่วนตามหน้าที่แต่เก็บในโปรเจกต์เดียวครับ apps/web เป็นหน้าจอ apps/api รับคำขอและคุยฐานข้อมูล packages/shared เก็บชนิดข้อมูลและกติกาที่ใช้ร่วมกัน workflow อยู่ใน n8n และคู่มืออยู่ใน docs root มีคำสั่งตรวจชนิดข้อมูล ทดสอบ และสร้างไฟล์เว็บ ส่วนคำสั่ง dev ใช้ concurrently เปิด Vite กับ Hono คู่กัน จุดนี้เป็นหน้าที่ของ script ไม่ใช่คุณสมบัติพิเศษของ monorepo ตัว monorepo ช่วยจัดโค้ด ส่วน npm workspaces ช่วยเชื่อมแพ็กเกจครับ

| `test` / `npm test` | รันข้อทดสอบที่ส่งข้อมูลเข้าแล้วตรวจผลตามเงื่อนไขที่กำหนด | ตรวจพฤติกรรม API ฐานข้อมูล และอีเมลกับตัวรับในเครื่อง ไม่ได้พิสูจน์ Gmail จริง |
| `typecheck` / `npm run typecheck` | ตรวจว่าการใช้ชื่อและชนิดข้อมูลในโค้ดสอดคล้องกันก่อนรัน | ตรวจทั้งเว็บกับ API แต่ไม่รับรองว่าทุกพฤติกรรมถูกต้อง |
| `npm run` | คำสั่งเรียกชื่อ script ที่โปรเจกต์กำหนดไว้ | ตามด้วย `dev`, `build` หรือ `typecheck`; `npm test` เป็นรูปแบบเรียก test ที่ใช้ได้เช่นกัน |

### คำถามที่อาจถูกถาม

**ถาม 1: ทำไมไม่คัดลอก schema ไปไว้ทั้งเว็บและ API?**  
ตอบ: ทำได้แต่เสี่ยงแก้ไม่พร้อมกันครับ การใช้ shared ทำให้สองฝั่งอ้างอิงกติกาเดียว เช่น แก้ความยาวชื่องานแล้วทั้งคู่รับกติกาเดียวกัน โดย API ยังต้องตรวจข้อมูลจริงทุกครั้ง

**ถาม 2: Monorepo แปลว่าต้องเปิดเว็บกับ API ใน process เดียวหรือไม่?**  
ตอบ: ไม่ครับ มันเป็นวิธีจัดโค้ด ช่วงพัฒนายังเปิด Vite และ Hono แยกกันได้ การเลือกรวมเสิร์ฟหลัง build เป็นการตัดสินใจอีกเรื่องหนึ่ง

**ใจความจำ:** Monorepo จัดโค้ดที่เกี่ยวข้องให้อยู่ด้วยกัน ส่วน shared ลดกติกาที่ต้องเขียนซ้ำ

อ่านเพิ่มเรื่องการเชื่อม package: [เอกสาร npm workspaces](https://docs.npmjs.com/cli/v11/using-npm/workspaces/)


## สไลด์ 06: Shared schema และการตรวจข้อมูล

**ที่มา:** PDF เดิม หน้า 05

### บทพูด

หน้านี้แสดงว่าทำไมต้องตรวจข้อมูลทั้งสองฝั่งครับ หน้าเว็บตรวจฟอร์มเพื่อบอกผู้ใช้ทันที เช่น ชื่องานสั้นเกินไป ส่วน API ตรวจซ้ำ เพราะคนเรียกอาจส่งคำขอเองโดยไม่ผ่านหน้าเว็บ ทั้งสองฝั่งใช้กติกาจาก shared ร่วมกัน ถ้าขอแก้งานแต่ส่งสถานะที่ไม่ยอมรับ API จะตอบ 400 และไม่เขียนข้อมูลงาน คำว่าไม่แตะ SQL บนสไลด์จึงต้องเข้าใจว่าไม่บันทึกข้อมูลผิด ไม่ได้หมายความว่าไม่มีการอ่านฐานข้อมูลเลย เพราะขั้นตรวจ session อาจอ่าน SQL ก่อนถึงการตรวจฟอร์ม

### ศัพท์และสัญลักษณ์ที่ต้องรู้

| คำบนสไลด์ | ความหมายแบบง่าย | ใช้ทำอะไรใน TaskFlow |
| --- | --- | --- |
| Shared schema | กติกาข้อมูลชุดเดียวที่หลายส่วนใช้ร่วมกัน | เว็บกับ API ตรวจชื่องาน วันที่ สถานะ และความสำคัญจากแพ็กเกจกลาง |
| Form — ฟอร์ม | กลุ่มช่องกรอกและปุ่มส่งข้อมูล | รับชื่องาน รายละเอียด ความสำคัญ และวันครบกำหนด |
| SQL boundary — เอสคิวแอล บาวน์ดะรี | จุดก่อนนำข้อมูลงานไปอ่านหรือเขียนผ่านคำสั่งฐานข้อมูล ไม่ใช่ชื่อเครื่องมือ | ต้องตรวจข้อมูลจากผู้เรียกก่อนนำไปใช้เปลี่ยนงาน |
| Frontend | ส่วนหน้าจอในเบราว์เซอร์ | ตรวจฟอร์มและแสดงข้อความผิดพลาดให้ผู้ใช้เห็นเร็ว |
| Backend | โปรแกรมฝั่งรับคำขอที่ผู้ใช้ไม่ควบคุมโค้ดโดยตรง | ตรวจข้อมูลซ้ำและตัดสินสิทธิ์ก่อนเปลี่ยนงาน |
| Tailwind | เครื่องมือใช้ชื่อรูปแบบสำเร็จจัดหน้าตาเว็บ | ทำสี ระยะห่าง และการปรับหน้าตาตามขนาดจอ ไม่ใช่ระบบตรวจสิทธิ์ |
| UI — User Interface | ส่วนที่คนเห็นและกดใช้งาน | ฟอร์ม ปุ่ม ตัวกรอง และข้อความแจ้งข้อผิดพลาด |
| Utility classes — ยูทิลิตี คลาสเซส | ชื่อรูปแบบเล็ก ๆ ที่แต่ละชื่อกำหนดเรื่องเดียว เช่น สีหรือระยะห่าง | นำชื่อหลายอันมาประกอบเพื่อจัดหน้าตา Tailwind โดยไม่ต้องเขียนรูปแบบใหม่ทุกครั้ง |
| Request — รีเควสต์ | คำขอจากโปรแกรมหนึ่งให้อีกโปรแกรมทำงาน พร้อมข้อมูลที่ต้องใช้ | เว็บส่งคำขอเพิ่มหรือแก้ข้อมูลงานไป API |
| PATCH — แพตช์ | ชนิดคำขอสำหรับแก้ข้อมูลเดิมบางส่วน | เปลี่ยนเฉพาะสถานะได้ โดยรายละเอียดและวันส่งที่ไม่ส่งมายังคงเดิม |
| Field — ฟิลด์ | ช่องข้อมูลที่มีชื่อและค่า | เช่น title คือชื่องาน และ status คือสถานะ ต้องผ่านกติกาของแต่ละช่อง |
| `400` | หมายเลขผลตอบกลับที่บอกว่าข้อมูลหรือคำขอไม่ถูกต้อง | ตัวอย่างสถานะงานผิดจากชุดที่ยอมรับ ได้ข้อผิดพลาดและไม่แก้ข้อมูล |
| SQL | ภาษาสั่งอ่านและเขียนฐานข้อมูลแบบตาราง | หลังผ่านกติกาจึงเขียนงาน แต่ขั้นตรวจ session อาจอ่าน SQL ก่อนหน้านั้นแล้ว |
| `→` | ลูกศรแสดงผลที่ตามมาหรือลำดับการทำงาน | ช่องข้อมูลผิด → ตอบ 400 → ไม่เขียนข้อมูลงาน |
| “ไม่แตะ SQL” | ข้อความย่อที่ต้องจำกัดความ ไม่ใช่คำรับรองว่าไม่มีคำสั่งฐานข้อมูลใดทำงาน | พูดให้แม่นว่า “ไม่เขียนข้อมูลงานจากข้อมูลที่ไม่ผ่าน” เพราะตรวจ session มีการอ่านฐานข้อมูล |

### คำถามที่อาจถูกถาม

**ถาม 1: หน้าเว็บตรวจแล้ว ทำไม API ต้องตรวจอีก?**  
ตอบ: เพราะผู้เรียกส่งคำขอเข้าตรงโดยไม่ผ่านฟอร์มได้ครับ หน้าจอช่วยลดการกรอกผิด ส่วน API เป็นจุดบังคับกติกา ถ้าเชื่อหน้าเว็บอย่างเดียว คนข้ามฟอร์มก็ข้ามกติกาได้

**ถาม 2: ถ้า PATCH ส่งแค่สถานะ ช่องรายละเอียดและวันที่จะหายหรือไม่?**  
ตอบ: ไม่หายครับ schema สำหรับแก้ไขรับเฉพาะช่องที่ส่งมา แล้ว backend รวมกับข้อมูลเดิม ต่างจากการสร้างงานที่มีค่าเริ่มต้น ถ้าส่งสถานะผิดจะได้ 400 โดยไม่เขียนข้อมูลใหม่

**ใจความจำ:** ตรวจหน้าเว็บเพื่อช่วยผู้ใช้ และตรวจที่ API เพื่อบังคับกติกากับทุกคำขอ

## สไลด์ 07: ER diagram ของฐานข้อมูล

**แผนที่หน้า:** สไลด์รวม 7 = PDF ต้นฉบับหน้า 06

### บทพูด

หน้านี้เป็นแผนผังฐานข้อมูลของ TaskFlow ครับ ผู้ใช้หนึ่งคนมีงาน เซสชัน และคีย์แจ้งเตือนได้หลายรายการ เราแยกข้อมูลเป็นหกตาราง เพราะมีหน้าที่และอายุต่างกัน ทุกตารางมีไอดีระบุแต่ละแถว ส่วนฟอเรนคีย์เชื่อมว่าแถวนั้นเกี่ยวข้องกับผู้ใช้หรืองานใด ตารางล่างเก็บประวัติแจ้งเตือน โดยห้ามบันทึกชุดเจ้าของ งาน วัน และช่องทางเดิมซ้ำ แต่ความสัมพันธ์ในฐานข้อมูลยังไม่ได้อนุญาตให้เปิดดูงาน ฝั่ง API ต้องตรวจเจ้าของด้วย ซึ่งผมจะอธิบายในหน้าถัดไป

### คำที่เห็นบนสไลด์

| คำ / สัญลักษณ์ | ความหมายง่าย ๆ และหน้าที่ใน TaskFlow |
|---|---|
| `ER diagram` | Entity–Relationship diagram คือแผนผังแสดงข้อมูลและความสัมพันธ์ กล่องแทนตาราง เส้นเชื่อมช่วยให้เห็นว่าข้อมูลผูกกันอย่างไร |
| `1:N` | อ่านว่า “หนึ่งต่อหลาย” เช่น ผู้ใช้หนึ่งคนมีงานได้หลายงาน ไม่ได้แปลว่าผู้ใช้ทุกคนต้องมีงานอย่างน้อยหนึ่งงาน |
| `id` | รหัสระบุแถว เช่น รหัสผู้ใช้หรือรหัสงาน การรู้ไอดีไม่ได้ทำให้มีสิทธิ์อ่านแถวนั้น |
| `PK` / `primary key` | คีย์หลัก ระบุแต่ละแถวไม่ซ้ำ ในระบบนี้ทุกตารางใช้ `id` เป็นคีย์หลัก |
| `FK` | Foreign key หรือคีย์อ้างอิง เชื่อมไปยังแถวที่มีอยู่จริง เช่น `user_id` อ้าง `users.id` ช่วยคุมความสัมพันธ์ แต่ไม่ได้ตรวจสิทธิ์ผู้เรียก API |
| `users` | ตารางบัญชีผู้ใช้ เป็นเจ้าของงาน เซสชัน คีย์ และลิงก์ตั้งรหัสผ่าน |
| `email` | อีเมลของบัญชี ใช้เข้าสู่ระบบและเป็นผู้รับลิงก์ตั้งรหัสผ่าน |
| `UNIQUE` หลัง `email` | ฐานข้อมูลไม่ยอมให้สองบัญชีใช้อีเมลที่เก็บไว้ค่าเดียวกัน |
| `auth_sessions` | ตารางการเข้าสู่ระบบ เก็บว่าเซสชันเป็นของใคร หมดอายุเมื่อไร และถูกยกเลิกหรือยัง |
| `user_id` | รหัสเจ้าของที่อ้างไปยัง `users.id` มีในตารางลูกจริง แม้ภาพย่อจะไม่ได้เขียนครบทุกกล่อง |
| `expires` / `revoked` | ป้ายย่อของสถานะหมดอายุและถูกยกเลิก ฟิลด์จริงของเซสชันคือ `expires_at` และ `revoked_at` |
| `password_reset_tokens` | ตารางหลักฐานลิงก์ตั้งรหัสผ่านใหม่ แต่ละรายการผูกกับบัญชีและมีเวลาหมดอายุ |
| `token_hash` | ค่า SHA-256 ที่คำนวณจาก reset token ใช้ค้นหาและตรวจ token โดยไม่เก็บ token ดิบใน SQL |
| `used` | ป้ายย่อของการใช้ลิงก์แล้ว ฟิลด์จริงคือ `used_at` ถ้ามีเวลาบันทึกอยู่ ลิงก์นั้นใช้ซ้ำไม่ได้ |
| `tasks` | ตารางงานส่วนตัวของผู้ใช้ |
| `status` | สถานะงาน: `pending` ยังไม่เริ่ม, `in_progress` กำลังทำ, `completed` เสร็จแล้ว |
| `priority` | ความสำคัญ: `low` ต่ำ, `medium` ปกติ, `high` สูง แยกจากสถานะว่าทำเสร็จหรือยัง |
| `due_date` | วันครบกำหนดงาน อาจไม่กำหนดก็ได้ ใช้เลือกงานถึงกำหนดเพื่อแจ้งเตือน |
| `api_keys` | ตารางคีย์สำหรับโปรแกรมภายนอก เช่น workflow แจ้งเตือนของ n8n |
| `secret_hash` | ผลแฮช SHA-256 ของ API key ที่ผู้เรียกส่งมา ใช้เก็บและตรวจเทียบแทนคีย์ดิบ |
| `scope` | ขอบเขตที่คีย์ทำได้ ระบบนี้ให้ค่า `reminders` สำหรับอ่านงานครบกำหนดและบันทึกการแจ้งเตือน |
| `expires` ใน `api_keys` | ป้ายย่อของ `expires_at` คีย์หมดอายุหลังสร้าง 30 วัน และยกเลิกก่อนกำหนดได้ |
| `reminder_deliveries` | ตารางประวัติที่บันทึกว่าระบบแจ้งเตือนได้รายงานการส่งของงานใดแล้ว |
| `task_id` | รหัสงานที่ประวัติแจ้งเตือนนั้นอ้างถึง เป็น FK ไปยัง `tasks.id` |
| `owner/task/day/channel` | ชื่อเรียกย่อของชุด `user_id`, `task_id`, `notification_date`, `channel` ไม่ใช่ชื่อฟิลด์เดียว |
| `UNIQUE` ของชุดแจ้งเตือน | ห้ามชุดทั้งสี่ค่าซ้ำร่วมกัน ไม่ได้ห้ามผู้ใช้คนเดิมหรืองานเดิมมีประวัติหลายวัน |
| `channel` | ช่องทางแจ้งเตือน ปัจจุบันรองรับ `email` |
| `•`, `+`, `/` และลูกศร | จุดใช้คั่นรายการ เครื่องหมายบวกหมายถึงใช้หลายฟิลด์ร่วมกัน ทับคั่นชื่อย่อ ลูกศรแสดงความสัมพันธ์ ไม่ใช่หลักฐานว่า API อนุญาตให้อ่านข้อมูล |

### คำถามที่น่าจะถูกถาม

**ถาม: มี FK แล้วทำไมยังต้องตรวจเจ้าของที่ API?**  
ตอบ: FK ตรวจว่ารหัสที่อ้างมีแถวอยู่จริง แต่ไม่ได้รู้ว่าคนส่งคำขอเป็นใคร จึงยังต้องใช้ `user_id` จากเซสชันตรวจเจ้าของทุกครั้ง

**ถาม: UNIQUE ในตารางแจ้งเตือนรับประกันว่าอีเมลจะไม่ส่งซ้ำเลยหรือไม่?**  
ตอบ: รับประกันว่าแถวประวัติชุดเดิมบันทึกซ้ำไม่ได้ แต่ถ้าส่งเมลแล้วโปรแกรมหยุดก่อนบันทึกประวัติ รอบถัดไปอาจส่งซ้ำได้ จึงยังไม่ใช่การส่งแบบครั้งเดียวแน่นอน

**ใจความจำ:** ตารางบอกว่าข้อมูลสัมพันธ์กันอย่างไร ส่วน API ต้องตรวจว่าใครมีสิทธิ์ใช้ข้อมูลนั้น

## สไลด์ 08: SQL ที่ตรวจเจ้าของงานจริง

**แผนที่หน้า:** สไลด์รวม 8 = สไลด์ทดแทน 04 เพิ่มหลัง PDF หน้า 06

### บทพูด

หน้านี้แสดงการตรวจเจ้าของงานจริง เราค้นหาทั้งไอดีงานและไอดีเจ้าของที่ต้องตรงกับผู้เข้าสู่ระบบ ไอดีงานมาจากคำขอ ส่วนไอดีผู้ใช้มาจากเซสชันที่เซิร์ฟเวอร์ตรวจแล้ว ไม่ให้ผู้เรียกกำหนดเจ้าของเอง เครื่องหมายคำถามเป็นช่องรับค่าผ่านพารามิเตอร์ ซึ่งแยกข้อมูลออกจากคำสั่ง SQL ถ้างานไม่มีหรือเป็นของคนอื่น ระบบตอบไม่พบเหมือนกัน การแก้ไขและลบงานใช้หลักเดียวกัน หัวใจคือรู้รหัสงานอย่างเดียว ยังเข้าถึงงานของผู้อื่นไม่ได้ครับ

### โค้ดบนสไลด์

```sql
SELECT id, title, status, priority, due_date
FROM tasks
WHERE id = ? AND user_id = ?
```

```js
db.prepare(sql).get(taskId, sessionUser.id)
```

### คำที่เห็นบนสไลด์

| คำ / สัญลักษณ์ | ความหมายง่าย ๆ และหน้าที่ใน TaskFlow |
|---|---|
| `SQL` | Structured Query Language ภาษาสั่งอ่านและแก้ข้อมูลในฐานข้อมูล ระบบนี้ใช้กับ SQLite |
| `SELECT` | เลือกว่าจะอ่านคอลัมน์ใดจากแถวที่เข้าเงื่อนไข |
| `id`, `title` | รหัสงานและชื่อของงาน |
| `status`, `priority`, `due_date` | สถานะ ความสำคัญ และวันครบกำหนด เป็นข้อมูลที่ส่งกลับไปแสดงหน้าจอ |
| `FROM tasks` | ระบุให้อ่านจากตารางงาน `tasks` |
| `WHERE` | เริ่มเงื่อนไขว่าจะแสดงแถวใด |
| `id = ?` | รหัสแถวต้องตรงกับไอดีงานที่ผูกเข้าตำแหน่งคำถามแรก |
| `AND` | เงื่อนไขด้านซ้ายและขวาต้องจริงพร้อมกัน จึงผ่านทั้งรหัสงานและเจ้าของ |
| `user_id = ?` | เจ้าของงานต้องตรงกับไอดีผู้ใช้ที่เซิร์ฟเวอร์ยืนยันแล้ว |
| `?` | Placeholder หรือช่องรอค่า ไม่ใช่การเอาข้อความผู้ใช้มาต่อเข้าคำสั่ง SQL |
| `parameter` | ค่าที่ผูกเข้าช่อง `?` ตามลำดับ เช่น รหัสงานและรหัสเจ้าของ |
| `db` | ตัวแทนการเชื่อมต่อฐานข้อมูลในตัวอย่าง |
| `sql` | ตัวแปรที่เก็บข้อความคำสั่ง SQL |
| `prepare(sql)` | เตรียมคำสั่งให้ผูกค่าข้อมูลแยกจากโครงคำสั่ง ช่วยป้องกัน SQL injection ที่มากับค่าข้อมูล |
| `.get(...)` | รันคำสั่งอ่านและรับแถวแรกที่ตรงเงื่อนไข ในตัวอย่างคือรายละเอียดงานหนึ่งรายการ |
| `taskId` | ตัวแปรรหัสงานที่ผู้เรียกต้องการเปิด |
| `sessionUser.id` | ชื่ออธิบายบนสไลด์ หมายถึงไอดีผู้ใช้จากเซสชันที่ตรวจแล้ว ในโค้ดจริงอ่านจาก `c.get('user').id` |
| `identity` | ตัวตนปัจจุบันที่ฝั่งเซิร์ฟเวอร์ยืนยันแล้ว ใช้ตัดสินว่าแถวเป็นของใคร |
| `session` | หลักฐานการเข้าสู่ระบบที่ผูกกับบัญชี ไม่ใช่ค่ารหัสผู้ใช้ที่เชื่อจาก body ได้ทันที |
| `404` | HTTP status “ไม่พบ” ใช้ทั้งกรณีไม่มีงานและงานไม่ได้เป็นของผู้ใช้ปัจจุบัน |
| `ID` | หมายเลขหรือรหัสระบุสิ่งหนึ่ง ในหน้านี้หมายถึงรหัสงาน ไม่ใช่สิทธิ์เข้าถึง |
| `=`, `,`, `.`, `(...)`, `/` | เท่ากับใช้เปรียบเทียบ จุลภาคแยกคอลัมน์หรืออาร์กิวเมนต์ จุดเข้าถึงสมาชิก วงเล็บครอบค่าที่ส่งให้ฟังก์ชัน ทับในคำอธิบายใช้คั่นประเด็น |

### คำถามที่น่าจะถูกถาม

**ถาม: ถ้าใช้ UUID เดายากแล้ว ยังต้องตรวจ `user_id` หรือไม่?**  
ตอบ: ต้องตรวจ เพราะไอดีอาจปรากฏในลิงก์หรือข้อมูลอื่น UUID เป็นตัวระบุ การตรวจเจ้าของต่างหากที่ให้สิทธิ์

**ถาม: Prepared SQL ป้องกันปัญหาได้ทุกอย่างหรือไม่?**  
ตอบ: ไม่ได้ มันแยกค่าข้อมูลออกจากโครงคำสั่ง แต่ยังต้องตรวจรูปแบบข้อมูลและสิทธิ์เจ้าของ และไม่ควรนำชื่อคอลัมน์จากผู้ใช้มาต่อคำสั่งโดยไม่จำกัดค่าที่อนุญาต

**ใจความจำ:** รหัสงานเลือกแถว ส่วนรหัสผู้ใช้จากเซสชันจำกัดว่าแถวนั้นเป็นของเรา

## สไลด์ 09: JWT, cookie และการเพิกถอน session

**แผนที่หน้า:** สไลด์รวม 9 = สไลด์ทดแทน 05 แทน PDF หน้า 07

### บทพูด

เมื่อเข้าสู่ระบบ เบราว์เซอร์ได้รับ JWT ผ่านคุกกี้ ภายในมีรหัสผู้ใช้ รหัสเซสชัน และเวลาหมดอายุ ข้อมูลอ่านได้ จึงไม่ใส่ความลับ ทุกคำขอที่เปิดงาน เซิร์ฟเวอร์ตรวจลายเซ็น ผู้ออกโทเคน ผู้รับ และเวลาหมดอายุ แล้วตรวจเซสชันในฐานข้อมูลว่ายังไม่หมดอายุและไม่ถูกยกเลิก เมื่อออกจากระบบ เราลบคุกกี้และยกเลิกเซสชัน ทำให้สำเนาโทเคนเดิมใช้ต่อไม่ได้ อายุเซสชันคือสามสิบนาที ยังไม่มีรีเฟรชโทเคนสำหรับต่ออายุ ถ้าหมดอายุ ผู้ใช้ต้องเข้าสู่ระบบใหม่ครับ

### คำที่เห็นบนสไลด์

| คำ / สัญลักษณ์ | ความหมายง่าย ๆ และหน้าที่ใน TaskFlow |
|---|---|
| `JWT` | JSON Web Token เป็นรูปแบบโทเคน ระบบนี้ใช้แบบลงลายเซ็น มี header, payload และ signature ไม่ได้เข้ารหัสซ่อนเนื้อหา |
| `header` | ส่วนบอกวิธีตรวจ token เช่นระบุว่าใช้อัลกอริทึม HS256 ไม่ใช่รหัสผ่าน |
| `payload` | ส่วนข้อมูลที่ token ระบุ เช่น sub, sid และ exp ผู้ถือ token อ่านส่วนนี้ได้ จึงไม่ใส่รหัสผ่านหรือความลับ |
| `signature` | ค่าตรวจที่คำนวณจาก header, payload และกุญแจลับ เซิร์ฟเวอร์ใช้ตรวจว่าข้อมูลถูกแก้หรือออกโดยผู้ที่ไม่มีกุญแจลับหรือไม่ |
| `cookie` / `Cookie JWT` | ข้อมูลที่เบราว์เซอร์เก็บและแนบให้เซิร์ฟเวอร์ตามกติกา TaskFlow ใส่ JWT ในคุกกี้ชื่อ `taskflow_session` |
| `sub` | Subject รหัสผู้ใช้ที่โทเคนกล่าวถึง ในระบบนี้เป็น `users.id` |
| `sid` | Session ID รหัสเซสชันที่ระบบเพิ่มใน payload ใช้เชื่อมกับ `auth_sessions.id` |
| `exp` | Expiration time เวลาหมดอายุของ JWT เป็นจำนวนวินาทีที่นับจากวันที่ 1 มกราคม 1970 ตามเวลามาตรฐานสากล ตรวจว่าโทเคนยังไม่หมดอายุ |
| `verify signature` | ตรวจลายเซ็นเพื่อยืนยันว่าโทเคนไม่ถูกแก้และลงนามด้วยคีย์ที่ระบบเชื่อ ไม่ใช่การถอดรหัส payload |
| `HS256` | HMAC using SHA-256 คือการสร้างค่าตรวจข้อความด้วยกุญแจลับและ SHA-256 ระบบนี้ใช้กุญแจลับเดียวกันตอนออกและตรวจ token และอนุญาตวิธีนี้โดยเจาะจง |
| `iss` | Issuer ผู้ที่ออกโทเคน ระบบกำหนดให้เป็น `taskflow` |
| `aud` | Audience ผู้รับที่ตั้งใจให้ใช้โทเคน ระบบกำหนดให้เป็น `taskflow-web` |
| `SQL session` | แถวการเข้าสู่ระบบในฐานข้อมูล ตรวจว่าผูกกับผู้ใช้ใน JWT ไม่หมดอายุ และยังไม่ถูกเพิกถอน |
| `session` | การเข้าสู่ระบบหนึ่งครั้ง ผู้ใช้หนึ่งคนอาจมีหลายเซสชัน เช่น เปิดใช้จากคนละอุปกรณ์ |
| `revoke` | เพิกถอนหรือยกเลิกสิทธิ์เซสชัน แม้ JWT จะยังมีเวลาเหลือก็ต้องถูกปฏิเสธ |
| `revoked_at` | เวลาที่เซสชันถูกเพิกถอน ถ้ายังไม่มีค่าจึงยังผ่านเงื่อนไขส่วนนี้ |
| `Logout` | การออกจากระบบ โค้ดตั้ง `revoked_at` ของเซสชันปัจจุบัน แล้วลบคุกกี้ |
| `refresh token` | โทเคนสำหรับขอ access token ชุดใหม่ ระบบนี้ยังไม่ได้ทำ จึงต้อง login ใหม่เมื่อครบอายุ |
| `30 นาที` | อายุ JWT และเซสชันที่ระบบนี้กำหนด ไม่ใช่อายุรหัสผ่านของบัญชี |
| `+` และลูกศร | หมายถึงต้องตรวจหลายส่วนประกอบกัน และลำดับการตรวจ ไม่ใช่คำสั่งให้บวกค่าของฟิลด์ |

### คำถามที่น่าจะถูกถาม

**ถาม: JWT มีลายเซ็นแล้ว ทำไมต้องอ่าน SQL session อีก?**  
ตอบ: ลายเซ็นยืนยันโทเคน แต่ไม่บอกว่าเราเพิ่ง logout หรือ reset ไปหรือไม่ แถวเซสชันทำให้ยกเลิกโทเคนที่ยังไม่หมดอายุได้ แลกกับการอ่านฐานข้อมูลทุกคำขอที่ต้อง login

**ถาม: ถ้าลบคุกกี้อย่างเดียวพอหรือไม่?**  
ตอบ: ไม่พอ ถ้ามีสำเนา JWT อยู่ก่อนหน้า มันอาจยังผ่านการตรวจลายเซ็นได้ จึงต้อง revoke เซสชันด้วย และไม่ได้พึ่งว่าผู้ใช้จะลบสำเนาให้เรา

**ใจความจำ:** JWT ต้องตรวจผ่าน และเซสชันในฐานข้อมูลต้องยังใช้ได้ จึงจะอนุญาตคำขอ

อ้างอิงความหมาย JWT และ claims: [RFC 7519](https://datatracker.ietf.org/doc/html/rfc7519) ส่วน sid และอายุ 30 นาทีเป็นสิ่งที่ TaskFlow กำหนดเอง


## สไลด์ 10: JWT, API key และ reset token

**แผนที่หน้า:** สไลด์รวม 10 = สไลด์ทดแทน 06 แทน PDF หน้า 08

### บทพูด

หลักฐานสามชนิดมีหน้าที่ต่างกัน JWT ใช้กับผู้ใช้เว็บ API key ให้ n8n เรียกงานแจ้งเตือน ส่วน reset token ใช้เฉพาะตั้งรหัสผ่านใหม่ อายุจึงต่างกัน ฐานข้อมูลเก็บแฮชของคีย์และลิงก์แทนค่าดิบ ส่วนรหัสผ่านใช้เอสคริปต์ร่วมกับซอลต์ เพราะรหัสที่คนตั้งอาจเดาง่ายกว่าโทเคนสุ่ม แฮชไม่ใช่การเข้ารหัสที่มีคีย์ถอดกลับ เมื่อรีเซ็ตสำเร็จ ระบบยกเลิกทุกเซสชันและลิงก์รีเซ็ตที่ค้าง แต่ API key ต้องยกเลิกแยกครับ

### คำที่เห็นบนสไลด์

| คำ / สัญลักษณ์ | ความหมายง่าย ๆ และหน้าที่ใน TaskFlow |
|---|---|
| `JWT + SQL session` | หลักฐานผู้ใช้เว็บแบบตรวจทั้งโทเคนลงลายเซ็นและแถวเซสชันในฐานข้อมูล อายุ 30 นาที |
| `API key` | ค่าลับสำหรับโปรแกรมภายนอก ระบบสร้างคีย์ให้บัญชีหนึ่งและจำกัดหน้าที่ ไม่ใช่สิทธิ์เข้าทุก API |
| `n8n` | โปรแกรมจัด workflow อัตโนมัติ ในงานนี้เป็นผู้เรียก API เพื่อตรวจงานและส่งแจ้งเตือน |
| `reminders` | หน้าที่แจ้งเตือน เป็น scope ของ API key ใน TaskFlow ใช้อ่านงานถึงกำหนดและบันทึกการแจ้งเตือน |
| `Reset token` | ค่าลับสุ่มในลิงก์ตั้งรหัสผ่านใหม่ ไม่ใช่ JWT และใช้แทนการ login เพื่อจัดการงานไม่ได้ |
| `token` | หลักฐานลับที่ผู้ถือส่งให้ระบบตรวจ ความหมายและสิทธิ์ขึ้นกับชนิด ไม่ใช่ทุก token จะใช้แทนกันได้ |
| `cookie` | ที่เก็บ JWT ฝั่งเบราว์เซอร์ ซึ่งแนบไปกับคำขอของเว็บตามขอบเขตที่ตั้ง |
| `HttpOnly` | คุณสมบัติคุกกี้ที่ไม่ให้ JavaScript อ่านค่าคุกกี้โดยตรง เบราว์เซอร์ยังแนบคุกกี้ให้คำขอได้ แต่ยังไม่ได้ห้ามโค้ดบนหน้าเว็บส่งคำขอในตัวตนของผู้ใช้ จึงยังต้องตรวจแหล่งที่มาและสิทธิ์ที่ backend |
| `x-api-key` | ชื่อ HTTP header ที่ n8n ใช้ส่งค่าลับ API key ให้ backend ไม่ส่งคีย์ผ่านช่องค้นหาหรือลิงก์ |
| `SQL เก็บ` | ข้อมูลที่คงอยู่ใน SQLite สำหรับตรวจการใช้หลักฐาน ไม่ได้หมายความว่าเก็บ JWT หรือ token ดิบทุกชนิด |
| `SHA-256` | ฟังก์ชันแฮชที่ให้ผลลัพธ์ขนาดคงที่ ระบบใช้กับคีย์และ reset token ที่สุ่มด้วยความยาวสูง |
| `digest` | ผลลัพธ์ที่ได้จากการแฮช ระบบแฮชค่าที่รับมาแล้วค้นหาหรือเปรียบเทียบ ไม่ได้ถอด digest กลับเป็น token |
| `hash` | การแปลงข้อมูลเป็นผลลัพธ์ทางเดียว การแฮชแตกต่างจาก encryption ซึ่งออกแบบให้ถอดกลับด้วยคีย์ |
| `scrypt` | อ่านว่า “เอสคริปต์” ฟังก์ชันสำหรับแฮชรหัสผ่าน ใช้เวลาและทรัพยากรมากกว่า SHA-256 เพื่อเพิ่มต้นทุนการลองเดารหัส |
| `salt` | ค่าสุ่มใหม่ต่อการแฮชรหัสผ่าน ช่วยให้รหัสเหมือนกันได้ผลแฮชต่างกัน เก็บร่วมกับแฮชได้และไม่ใช่คีย์ถอดรหัส |
| `credential` | หลักฐานที่ใช้ยืนยันสิทธิ์ เช่น JWT, API key หรือ reset token ต้องเลือกให้ตรงหน้าที่ของ endpoint |
| `logout` | ยกเลิกเซสชันที่ใช้ออกจากระบบและลบคุกกี้ |
| `reset` | การตั้งรหัสผ่านใหม่ เมื่อสำเร็จจะ revoke เซสชันทั้งหมดและทำให้ลิงก์ reset ที่ค้างใช้ต่อไม่ได้ |
| `revoke` | ผู้ใช้หรือระบบยกเลิกสิทธิ์ก่อนครบอายุ เช่น ยกเลิก API key ที่หน้าเว็บ |
| `expiry` | การหมดอายุตามเวลาที่กำหนด แม้ยังไม่เคยใช้ก็ต้องถูกปฏิเสธเมื่อถึงเวลา |
| `30 นาที / 30 วัน / 15 นาที` | อายุ JWT+session / API key / reset token ตามลำดับ ไม่ใช่อายุรหัสผ่าน |
| `/`, `+`, `SHA-256` ที่มีขีด | ทับคั่นทางเลือกหรือรายการ บวกหมายถึงใช้ร่วมกัน ส่วนขีดใน SHA-256 เป็นส่วนหนึ่งของชื่อ ไม่ใช่การลบเลข |

### คำถามที่น่าจะถูกถาม

**ถาม: ทำไมรหัสผ่านไม่ใช้ SHA-256 เหมือน API key?**  
ตอบ: รหัสผ่านที่คนตั้งอาจเดาได้จากรายการคำทั่วไป จึงใช้ scrypt ที่ลองแต่ละครั้งแพงกว่าและมี salt ส่วนคีย์กับ reset token เป็นค่าสุ่ม 32 bytes จึงใช้ SHA-256 สำหรับตรวจและค้นหาได้

**ถาม: รีเซ็ตรหัสผ่านแล้ว API key ใช้ต่อได้หรือไม่?**  
ตอบ: โค้ดปัจจุบันยังใช้ต่อได้จนกว่าจะ revoke หรือหมดอายุ การ reset ยกเลิกเซสชันเว็บกับลิงก์ reset แต่ไม่ได้ยกเลิก API key อัตโนมัติ ถ้าสงสัยว่าคีย์รั่วต้องยกเลิกแยก

**ใจความจำ:** หลักฐานแต่ละชนิดมีหน้าที่ อายุ และเงื่อนไขยกเลิกต่างกัน จึงใช้แทนกันไม่ได้

## สไลด์ 11: ลำดับการขอลิงก์และตั้งรหัสผ่านใหม่

**แผนที่หน้า:** สไลด์รวม 11 = PDF ต้นฉบับหน้า 09

### บทพูด

อ่านแผนภาพจากบนลงล่าง ผู้ใช้ส่งอีเมลขอลิงก์ หากมีบัญชีและยังขอได้ ระบบสุ่มโทเคน เก็บแฮชกับเวลาหมดอายุ แล้วตอบข้อความกลางก่อนส่งเมล ข้อความที่เหมือนกันช่วยไม่เปิดเผยว่าอีเมลใดมีบัญชี ผู้ใช้เปิดลิงก์แล้วส่งโทเคนพร้อมรหัสใหม่ให้ API ตรวจ เลขสองศูนย์สองแปลว่ารับคำขอ ไม่ได้ยืนยันว่าเมลถึงแล้ว หลักฐานปัจจุบันทดสอบตัวรับ SMTP ในเครื่อง ยังไม่ใช่ Gmail จริง และ n8n ไม่ได้ส่งลิงก์รีเซ็ตนี้ครับ

### คำที่เห็นบนสไลด์

| คำ / สัญลักษณ์ | ความหมายง่าย ๆ และหน้าที่ใน TaskFlow |
|---|---|
| `Browser` | โปรแกรมเว็บของผู้ใช้ ส่งอีเมลขอลิงก์ และแสดงฟอร์มตั้งรหัสผ่านใหม่ |
| `Hono` | เฟรมเวิร์ก backend ที่รับคำขอ เลือก handler ตรวจข้อมูล และเรียกฐานข้อมูลหรือบริการส่งเมล |
| `API` / `Hono API` | Application Programming Interface ช่องทางคำขอของเว็บ ในหน้านี้รับขอลิงก์และตั้งรหัสผ่านใหม่ |
| `SQLite` | ฐานข้อมูล SQL แบบไฟล์ที่ backend เปิดใช้งาน เก็บบัญชีและหลักฐาน token |
| `Gmail` | ผู้ให้บริการอีเมลที่ตั้งค่าเป็นผู้ส่งได้ เป็นปลายทางของแผนการตั้ง SMTP ไม่ใช่หลักฐานว่างานนี้ส่งจริงแล้ว |
| `SMTP` | Simple Mail Transfer Protocol วิธีที่ backend ติดต่อบริการส่งอีเมล ในระบบใช้ Nodemailer เป็นตัวส่ง |
| `link` | ลิงก์ที่เปิดหน้าตั้งรหัสผ่านใหม่และบรรทุก reset token ผู้ได้ลิงก์จึงควรรักษาเป็นความลับ |
| `email` | อีเมลที่กรอกเพื่อค้นหาบัญชีและระบุผู้รับลิงก์ กรณีไม่พบบัญชียังตอบข้อความกลาง |
| `hash` | ในขั้นนี้หมายถึง SHA-256 digest ของ reset token ไม่ใช่ password hash และไม่ใช่ token ดิบ |
| `expiry` | เวลาหมดอายุของลิงก์ กำหนด 15 นาทีหลังสร้าง แล้ว backend ตรวจอีกครั้งตอนใช้งาน |
| `202` | HTTP Accepted รับคำขอไว้แล้ว ไม่รับประกันว่า SMTP สำเร็จหรืออีเมลอยู่ใน inbox ใช้เมื่อบริการส่งเมลถูกตั้งค่าแล้ว |
| `async` | Asynchronous งานส่งเมลเริ่มหลังตอบคำขอ จึงไม่รอเครือข่าย SMTP ใน response ปัจจุบันอยู่ใน process ยังไม่ใช่คิวงานที่ทนต่อการรีสตาร์ต |
| `POST` | HTTP method สำหรับส่งข้อมูลให้เซิร์ฟเวอร์ดำเนินการ ในลูกศรสุดท้ายใช้ส่ง token และรหัสผ่านใหม่ |
| `token` | ค่าลับจากลิงก์ที่พิสูจน์ว่าผู้ขอมีสิทธิ์ตั้งรหัสของบัญชีนั้น ต้องยังไม่หมดอายุและไม่เคยใช้ |
| `password` | รหัสผ่านใหม่ที่ผู้ใช้ต้องการตั้ง ส่งให้ backend ตรวจแล้วสร้าง scrypt hash ไม่เก็บค่าดิบใน SQL |
| `+` | หมายถึงส่งหรือเก็บข้อมูลทั้งสองอย่างร่วมกัน เช่น hash กับ expiry ไม่ใช่การบวกตัวเลข |
| เส้นประแนวตั้ง / ลูกศรแนวนอน | เส้นประเป็นช่วงเวลาของแต่ละส่วน ลูกศรเป็นการส่งข้อมูลหรือลำดับการติดต่อ ให้อ่านจากบนลงล่าง ภาพย่อไม่ได้รับรองว่าอีเมลส่งถึงแล้ว |

### คำถามที่น่าจะถูกถาม

**ถาม: ถ้าได้ 202 แล้วทำไมยังไม่ได้เมล?**  
ตอบ: 202 ยืนยันเพียงรับคำขอ อาจไม่มีบัญชี ติดช่วงเว้นการขอ หรือส่งเมลล้มเหลวก็ได้ ระบบตอบกลางเพื่อความเป็นส่วนตัว และต้องตรวจการตั้งค่ากับผู้ให้บริการจริงแยกจากผล HTTP

**ถาม: ทำไมไม่ตอบตรง ๆ ว่าอีเมลนี้ไม่มีบัญชี?**  
ตอบ: จะเปิดช่องให้คนภายนอกลองไล่รายชื่อบัญชีได้ จึงตอบข้อความเดียวกันทั้งกรณีพบและไม่พบบัญชี แต่ยังมี rate limit และการจำกัดการส่งต่อบัญชี

**ใจความจำ:** รับคำขอขอลิงก์สำเร็จ เป็นคนละเรื่องกับส่งเมลถึงผู้รับสำเร็จ

## สไลด์ 12: Token ใช้ครั้งเดียวและ transaction

**แผนที่หน้า:** สไลด์รวม 12 = สไลด์ทดแทน 07 แทน PDF หน้า 10

### บทพูด

ระบบคำนวณแฮชรหัสใหม่ก่อนเริ่มทรานแซกชัน เพื่อไม่ล็อกฐานข้อมูลระหว่างคำนวณ จากนั้นยืนยันสิทธิ์ใช้โทเคนอีกครั้ง ถ้ายังไม่ใช้และไม่หมดอายุจึงเปลี่ยนรหัส ยกเลิกเซสชัน และปิดลิงก์รีเซ็ตที่ค้าง ทุกขั้นต้องสำเร็จพร้อมกัน ถ้าผิดพลาดจะย้อนกลับทั้งชุด แม้สองคำขอใช้ลิงก์เดียวกันพร้อมกัน ก็สำเร็จได้เพียงหนึ่งคำขอ ส่วนล็อกอินที่กำลังตรวจรหัสเดิมขณะรีเซ็ต ต้องอ่านแฮชล่าสุดก่อนออกเซสชัน สุดท้ายให้ผู้ใช้เข้าสู่ระบบใหม่เองครับ

### คำที่เห็นบนสไลด์และคำที่ใช้ตอบขั้นตอนนี้

| คำ / สัญลักษณ์ | ความหมายง่าย ๆ และหน้าที่ใน TaskFlow |
|---|---|
| `Token` | ในหน้านี้คือ reset token ไม่ใช่ JWT และไม่ได้ใช้เรียกงานทั่วไป |
| `32 bytes` | ความยาวข้อมูลสุ่ม 32 ไบต์ เท่ากับ 256 บิต โค้ดแสดงเป็นเลขฐานสิบหก 64 ตัวอักษร ไม่ใช่รหัสผ่านยาว 32 ตัวอักษร |
| `SQL เก็บ SHA-256` | เก็บผลแฮช SHA-256 ของ token ใน `token_hash` ส่วนค่าดิบอยู่ในลิงก์ที่ส่งให้ผู้รับ |
| `15 นาที` | อายุ reset token นับจากสร้าง ไม่ใช่ช่วงเวลาที่ปล่อยให้ใช้ซ้ำได้ |
| `ใช้ token ครั้งเดียว` / `single use` | token ที่ใช้สำเร็จแล้วถูกทำเครื่องหมาย จึงเปลี่ยนรหัสผ่านรอบที่สองด้วย token เดิมไม่ได้ |
| `transaction` | กลุ่มการเปลี่ยนข้อมูลที่ต้องสำเร็จทั้งหมดหรือย้อนกลับทั้งหมด ในที่นี้รวม claim token เปลี่ยนรหัส และยกเลิกหลักฐานเก่า |
| `Claim token` | ขอสิทธิ์ใช้ token ด้วยคำสั่งแก้ไขที่มีเงื่อนไข ไม่ใช่แค่อ่านว่ามันยังว่าง โค้ดบังคับว่ายังไม่ใช้และยังไม่หมดอายุ แล้วตรวจว่าเปลี่ยนได้หนึ่งแถวจริง |
| `password hash` | ค่าแฮชรหัสผ่านใหม่ที่คำนวณด้วย scrypt และ salt ไว้ก่อนเริ่ม transaction ไม่ใช่รหัสผ่านดิบ |
| `scrypt` | ฟังก์ชันแฮชรหัสผ่านที่ใช้ทรัพยากรเพื่อเพิ่มต้นทุนการเดารหัส ขั้นคำนวณนี้ทำก่อนถือ transaction |
| `Revoke` | ตั้งเวลายกเลิกทุกเซสชันของบัญชี ทำให้ JWT เก่าไม่ผ่านการตรวจ session อีก |
| `session` | การเข้าสู่ระบบแต่ละครั้งที่เก็บใน `auth_sessions` ผู้ใช้หนึ่งคนมีหลายรายการได้ |
| `reset` / ลิงก์ reset ทั้งหมด | การตั้งรหัสใหม่สำเร็จทำให้ลิงก์ที่ค้างของบัญชีเดียวกันใช้ไม่ได้ด้วย แต่ไม่แตะลิงก์ของผู้ใช้คนอื่น |
| `Login` | การตรวจอีเมลและรหัสผ่านเพื่อสร้างเซสชันใหม่ หลัง reset ผู้ใช้ต้องทำขั้นตอนนี้เอง |
| `hash ปัจจุบัน` | ค่า `password_hash` ที่อ่านใหม่จากบัญชีก่อนสร้างเซสชัน ถ้าต่างจากค่าที่เพิ่งตรวจรหัส แปลว่ารหัสเปลี่ยนระหว่างรอ จึงไม่ออกเซสชันจากผลเก่า |
| `commit` | ยืนยันการเปลี่ยนข้อมูลทั้ง transaction ให้มีผลถาวร หลังจากนั้นจึงตอบสำเร็จและให้ login ใหม่ |
| `rollback` | ย้อนการเปลี่ยนข้อมูลใน transaction ถ้ามีขั้นใดล้มเหลว ไม่ปล่อยให้เปลี่ยนรหัสสำเร็จเพียงครึ่งชุด |
| `race` | เหตุการณ์ที่คำขอทำงานซ้อนกันและผลขึ้นกับจังหวะ เช่น สองคำขอ reset พร้อมกัน หรือ login รหัสเดิมซ้อนกับ reset |
| `1–4` และลูกศร | ลำดับการเปลี่ยนข้อมูลใน transaction ไม่ได้รวมการคำนวณ scrypt ซึ่งเกิดก่อนเริ่ม และไม่ได้รวม login ใหม่ซึ่งเกิดหลัง commit |

### คำถามที่น่าจะถูกถาม

**ถาม: อ่านว่า token ยังไม่ใช้แล้วค่อยเปลี่ยนรหัสเลยได้หรือไม่?**  
ตอบ: ยังไม่พอ เพราะสองคำขออาจอ่านเจอว่ายังไม่ใช้พร้อมกัน โค้ดจึง claim ภายใน transaction ด้วยเงื่อนไข `used_at IS NULL` และ `expires_at > ?` แล้วตรวจว่ามีแถวถูกเปลี่ยนหนึ่งแถว ผู้แพ้ต้องถูกปฏิเสธ

**ถาม: ทำไมตรวจรหัสตอน login ผ่านแล้ว ยังต้องอ่านแฮชล่าสุดอีก?**  
ตอบ: การตรวจ scrypt มีช่วงรอ ระหว่างนั้น reset อาจเปลี่ยนรหัสสำเร็จแล้ว ถ้าออกเซสชันจากผลตรวจเดิมจะเปิดทางให้รหัสเก่าใช้ต่อได้ จึงต้องเทียบแฮชปัจจุบันก่อนสร้างเซสชัน

**ใจความจำ:** ตรวจซ้ำตอนใช้จริง เปลี่ยนข้อมูลเป็นชุดเดียว และไม่ออกเซสชันจากรหัสผ่านที่เปลี่ยนไปแล้ว

## สไลด์ 13: หน้าตั้งรหัสผ่านใหม่ที่รันจริง

ตรงกับไฟล์สไลด์ทดแทนหน้า 08 ใช้แทน PDF เดิมหน้า 11

### บทพูด

หน้านี้คือหน้าตั้งรหัสผ่านใหม่ที่รันจริงครับ ผู้ใช้เปิดลิงก์อีเมล แล้วกรอกรหัสใหม่ 12 ถึง 128 ตัวอักษร พร้อมยืนยันให้ตรงกัน หน้าเว็บอ่าน token เข้า memory แล้วลบออกจากแถบที่อยู่ทันที เพื่อลดการทิ้งลิงก์ที่มีสิทธิ์เปลี่ยนรหัสไว้ ถ้า refresh ค่าใน memory จะหาย จึงต้องเปิดลิงก์ต้นฉบับจากอีเมลอีกครั้ง โดยลิงก์ต้องยังไม่หมดอายุและไม่ถูกใช้ เมื่อบันทึกสำเร็จ ระบบยกเลิก session เดิมทุกอัน แล้วให้ผู้ใช้เข้าสู่ระบบใหม่ด้วยรหัสใหม่

### คำศัพท์และหน้าที่

| คำที่พบ | ความหมายแบบเข้าใจง่ายและหน้าที่ใน TaskFlow |
|---|---|
| TaskFlow | ชื่อระบบจัดการงานส่วนตัวที่นำเสนอ |
| token | ค่าสุ่มที่ใช้เป็นหลักฐานชั่วคราวว่าผู้เปิดลิงก์มีสิทธิ์ตั้งรหัสใหม่ ไม่ใช่รหัสผ่านเดิมและไม่ใช่ JWT |
| `#token` / fragment | ส่วนท้าย URL หลังเครื่องหมาย `#` หน้าเว็บอ่านค่านี้ได้ เบราว์เซอร์ไม่แนบ fragment ไปกับ HTTP request เปิดหน้า แต่เว็บจะส่ง token ใน body เมื่อตั้งรหัสใหม่ |
| URL / แถบที่อยู่ | ที่อยู่ของหน้าเว็บที่เบราว์เซอร์แสดง ต้องลบส่วนที่มี token หลังอ่านค่า |
| memory | หน่วยความจำชั่วคราวของหน้าเว็บ หน้านี้เก็บ token ไว้ระหว่างใช้งาน ไม่ได้เก็บให้คงอยู่หลัง reload |
| refresh / reload | โหลดหน้าเว็บใหม่ ทำให้ค่าชั่วคราวของหน้านี้หาย ต้องเปิดลิงก์อีเมลเดิมอีกครั้งหากยังใช้ได้ |
| 12–128 ตัวอักษร | ความยาวรหัสผ่านใหม่ที่ระบบยอมรับ ตรวจจริงที่ API ด้วย ไม่ได้อาศัยข้อความบนฟอร์มอย่างเดียว |
| ยืนยันรหัสผ่าน | ช่องกรอกซ้ำเพื่อช่วยป้องกันการพิมพ์ผิด หน้าเว็บตรวจว่าเหมือนกัน แล้วส่งเพียง `{ token, password }` ไป API |
| password | ฟิลด์รหัสผ่านใหม่ที่ส่งไป API ไม่ใช่ค่า hash ในฐานข้อมูล |
| login / เข้าสู่ระบบ | การยืนยันอีเมลและรหัสผ่านเพื่อเปิด session ใหม่ หลัง reset สำเร็จระบบไม่ login ให้อัตโนมัติ |
| session | สถานะการเข้าสู่ระบบที่อ้างอิงใน SQL เมื่อ reset สำเร็จ session เดิมทุกอันถูกยกเลิก |
| Gmail / inbox | บริการอีเมลและกล่องขาเข้า ภาพหน้านี้เป็นหลักฐาน UI ไม่ใช่หลักฐานการส่งอีเมลถึง inbox |

### คำถามที่อาจถูกถาม

- **ทำไม refresh แล้วใช้ต่อไม่ได้?** token อยู่ใน memory และถูกลบจาก URL ตั้งแต่เปิดหน้า เมื่อโหลดใหม่ต้องกลับไปเปิดลิงก์อีเมลต้นฉบับ ซึ่งยังต้องผ่านเงื่อนไขอายุและการใช้ครั้งเดียวครับ
- **reset แล้วผู้ที่ login อยู่จะยังใช้งานได้ไหม?** session เดิมทั้งหมดใช้ต่อไม่ได้ ต้อง login ใหม่ แต่ API key เป็นสิทธิ์อีกชนิดและไม่ได้ถูกยกเลิกด้วยขั้นตอนนี้

**ใจความจำ:** อ่าน token แล้วลบจาก URL ทันที ตั้งรหัสสำเร็จแล้วเข้าสู่ระบบใหม่ด้วยรหัสใหม่

## สไลด์ 14: ตั้ง Gmail SMTP และขอบเขตหลักฐาน

ตรงกับไฟล์สไลด์ทดแทนหน้า 09 ใช้แทน PDF เดิมหน้า 12

### บทพูด

การส่งอีเมลตั้งรหัสใหม่ทำจาก backend ไม่ต้องเปิด n8n ครับ เริ่มจาก setup เพื่อเติมค่าที่ขาด แล้วใส่ Gmail App Password ในเครื่อง ตั้ง APP_PUBLIC_URL ให้ผู้รับเปิดถึง คำสั่ง mail:check ตรวจการเชื่อมต่อและยืนยันตัวตน แต่ไม่ส่งอีเมล สิ่งที่ผ่านแล้วคือ SMTP receiver ในเครื่อง ยังไม่มีหลักฐาน Gmail ถึง inbox การส่งเป็น async ใน process เดียว ไม่มีคิวถาวร ถ้าโปรแกรมหยุดอาจต้องขอลิงก์ใหม่ และ SMTP ยอมรับข้อความก็ยังไม่ยืนยันว่าเข้ากล่องรับ

### คำศัพท์และหน้าที่

| คำที่พบ | ความหมายแบบเข้าใจง่ายและหน้าที่ใน TaskFlow |
|---|---|
| backend | ฝั่งเซิร์ฟเวอร์ของระบบ เป็นผู้สร้างลิงก์และติดต่อ SMTP เพื่อส่งอีเมล reset |
| Gmail | ผู้ให้บริการอีเมลที่เลือกเป็นบัญชีผู้ส่ง ผู้รับไม่จำเป็นต้องใช้ Gmail |
| SMTP — Simple Mail Transfer Protocol | วิธีที่โปรแกรมใช้ส่งอีเมลไปยังเซิร์ฟเวอร์เมล TaskFlow ใช้ส่งลิงก์ตั้งรหัสใหม่ |
| `npm run setup:email` | คำสั่งเติมช่องตั้งค่าอีเมลที่ขาดใน `.env` โดยไม่ทับค่าที่มีอยู่ ไม่ได้สร้างบัญชี Gmail หรือเปิดใช้ App Password ให้ |
| npm | เครื่องมือจัดการ package และเรียกคำสั่งที่กำหนดในโครงการ `npm run` ใช้เลือก script ตามชื่อ |
| Gmail App Password | รหัสเฉพาะสำหรับให้แอปเชื่อมบัญชี Google แทนรหัส Gmail ปกติ ต้องเปิดการยืนยันสองขั้นตอนก่อน ตัวเลือกอาจไม่ปรากฏในบัญชีงาน/สถานศึกษา บัญชีที่ใช้ security key เพียงอย่างเดียว หรือ Advanced Protection เก็บเฉพาะในเครื่อง ไม่ส่งในแชต |
| `.env` | ไฟล์ค่าตั้งค่าของเครื่อง เช่น บัญชี SMTP และรหัสสำหรับแอป ไม่ใช่ไฟล์สำหรับใส่ในสไลด์หรือเผยแพร่ |
| `APP_PUBLIC_URL` | ที่อยู่หน้าเว็บที่ใช้ประกอบลิงก์ในอีเมล ต้องเป็นที่อยู่ที่เครื่องผู้รับเข้าถึงได้ `localhost` ใช้ได้เฉพาะเครื่องที่รันเซิร์ฟเวอร์เอง |
| `npm run mail:check` | ตรวจการเชื่อมต่อ SMTP และการ login ตามค่าตั้งไว้ ไม่ส่งข้อความไปยังผู้รับ |
| Local SMTP receiver | เซิร์ฟเวอร์รับอีเมลที่เปิดในเครื่องสำหรับทดสอบการส่งจริง เป็นหลักฐานเส้นทางโปรแกรมถึงตัวรับในเครื่อง ไม่ใช่ Gmail จริง |
| inbox / Spam | กล่องขาเข้าและกล่องจดหมายขยะ ต้องตรวจหลังทดสอบส่งจริง เพราะการที่ SMTP รับข้อความยังไม่ยืนยันว่าเข้ากล่องขาเข้า |
| n8n | เครื่องมือทำ workflow แจ้งเตือนงาน เป็นส่วนเสริมอีกเส้นทางหนึ่ง ไม่จำเป็นต่อการ reset และใช้ SMTP credentials แยกกัน |
| token อายุ 15 นาที | ลิงก์มีสิทธิ์ตั้งรหัสได้ในช่วงสั้นและใช้ครั้งเดียว หมดอายุแล้วต้องขอใหม่ |
| 60 วินาที / 3 token ต่อชั่วโมง | ข้อจำกัดต่อบัญชี เว้นอย่างน้อย 60 วินาทีระหว่างคำขอ และสร้างได้ไม่เกิน 3 token ในช่วงหนึ่งชั่วโมงย้อนหลัง |
| async — asynchronous | รับคำขอแล้วส่งเมลต่อภายหลังใน process เดิม ผู้ใช้ได้คำตอบก่อนการส่งเสร็จ ไม่ได้หมายถึงมี worker หรือคิวถาวร |
| process | โปรแกรมที่กำลังทำงานหนึ่งชุด ถ้าชุดนี้หยุด งานส่งเมลที่ยังค้างใน memory อาจหาย |
| durable queue | คิวงานที่เก็บงานไว้ได้แม้โปรแกรมหยุด TaskFlow ยังไม่มีส่วนนี้ |

### คำถามที่อาจถูกถาม

- **mail:check ผ่านแล้วแปลว่าเมลถึงไหม?** ยังไม่แปลว่าถึงครับ คำสั่งนี้ไม่ส่งเมล ต้องทดลองขอลิงก์ด้วยอีเมลรับจริง แล้วตรวจ inbox และ Spam แยกต่างหาก
- **ถ้ารับ 202 แล้ว SMTP ส่งไม่สำเร็จเกิดอะไรขึ้น?** 202 หมายถึงรับคำขอไว้ ระบบส่งต่อแบบ async ถ้าส่งล้มเหลวจะลบ token ที่ยังไม่ใช้และบันทึกเหตุการณ์โดยไม่บันทึกความลับ แก้ค่าตั้งแล้วขอลิงก์ใหม่ได้ ไม่มีคิวถาวรรับประกันการส่งซ้ำ

**ใจความจำ:** ตรวจการเชื่อมต่อ ส่งจริง และยืนยันว่าเข้า inbox เป็นหลักฐานคนละขั้นกัน

## สไลด์ 15: การตรวจ request ก่อนแตะข้อมูล

ตรงกับไฟล์สไลด์ทดแทนหน้า 10 ใช้แทน PDF เดิมหน้า 13

### บทพูด

คำขอต้องผ่านหลายด่านก่อนแตะข้อมูลครับ ระบบใส่ request_id และ secure headers จำกัด body 16 KB และตรวจ Origin จากนั้นเลือก credential ตาม route งานส่วนตัวใช้ session ส่วน integrations ใช้ API key ข้อมูลต้องเป็น JSON และผ่าน Zod ก่อนทำ SQL ซึ่งต้องตรวจเจ้าของอีกชั้น ระบบจำกัด login กับ register รวม 20 ครั้งต่อ IP ใน 15 นาที ส่วน forgot-password 5 และ reset-password 10 ครั้ง ถ้าผิดพลาดจะคืน code ข้อความ และ request_id เพื่อค้นหาคำขอนั้น

### คำศัพท์และหน้าที่

| คำที่พบ | ความหมายแบบเข้าใจง่ายและหน้าที่ใน TaskFlow |
|---|---|
| request | คำขอจากเว็บหรือโปรแกรมภายนอกมายัง API เช่น อ่านรายการงานหรือบันทึกรหัสใหม่ |
| `request_id` | หมายเลขอ้างอิงคำขอ ใช้เชื่อมข้อความ error กับบันทึกฝั่งเซิร์ฟเวอร์ ไม่ใช่รหัสผู้ใช้ |
| secure headers | ส่วนหัว HTTP ตอบกลับที่ช่วยป้องกันพฤติกรรมบางลักษณะ เช่น `X-Content-Type-Options: nosniff` บอกเบราว์เซอร์ให้ยึดชนิดข้อมูลตาม `Content-Type` โดยไม่เดาเอง เป็นชั้นเสริม ไม่แทนการตรวจตัวตนหรือเจ้าของข้อมูล |
| HTTP — Hypertext Transfer Protocol | กติกาสื่อสารคำขอและคำตอบระหว่างผู้เรียกกับ API |
| 16KB limit / body | จำกัดข้อมูลในตัวคำขอไม่เกิน 16 × 1024 = 16,384 ไบต์ เพื่อลดการรับข้อมูลใหญ่เกินขอบเขตระบบนี้ |
| Origin guard | การตรวจต้นทางคำขอแก้ข้อมูล เช่น scheme โฮสต์และพอร์ตที่อนุญาต ลดการเรียกข้ามเว็บที่ไม่ยอมรับ ไม่ได้แทนการตรวจตัวตนหรือเจ้าของ |
| credential | หลักฐานที่ใช้แสดงสิทธิ์ เช่น session, API key หรือ reset token เลือกตรวจตาม route |
| route | กติกาจับคู่ HTTP method กับ path เพื่อเลือกว่าจะทำงานอะไร |
| Zod | ไลบรารีตรวจค่าจริงตอนรัน เช่น ความยาวชื่อ สถานะ วันที่ และรูปแบบ token |
| schema | กติกาว่าข้อมูลต้องมีฟิลด์ใดและค่าแบบไหน ใช้กรองข้อมูลก่อนทำงานกับฐานข้อมูล |
| JSON — JavaScript Object Notation | รูปแบบข้อมูลข้อความที่ API ใช้รับและตอบ เช่น `{ "email": "..." }` ไม่ใช่โค้ดที่ให้เซิร์ฟเวอร์นำไปรัน |
| JSON type / Content-Type | การระบุว่าตัวคำขอเป็น `application/json` ระบบตรวจชนิดนี้ด้วยเมื่อรับ JSON body |
| SQL — Structured Query Language | ภาษาสั่งอ่านและแก้ฐานข้อมูล คำสั่งของ TaskFlow ยังใส่เงื่อนไขเจ้าของงานด้วย |
| response | คำตอบจาก API มีสถานะ HTTP ส่วนหัว และข้อมูลตามแต่ละ route |
| IP — Internet Protocol address | ที่อยู่เครือข่ายที่ใช้เป็นหนึ่งในตัวนับการเรียก ไม่ใช่ตัวตนผู้ใช้ที่เชื่อถือแทน session ได้ |
| Login / register | เข้าสู่ระบบและสมัครบัญชี ใช้ตัวนับร่วมกัน 20 ครั้งต่อ IP ใน 15 นาที ไม่ใช่อย่างละ 20 |
| Forgot-password / Reset-password | ขออีเมลลิงก์และใช้ token ตั้งรหัสใหม่ จำกัด 5 และ 10 ครั้งต่อ IP ใน 15 นาทีตามลำดับ |
| Session / tasks / keys | session ใช้ยืนยันผู้ใช้เว็บเพื่อจัดการงานและ API key ของตนเอง `tasks` กับ `keys` เป็นกลุ่ม route |
| API — Application Programming Interface | ช่องทางที่เว็บหรือโปรแกรมอื่นเรียกใช้ความสามารถของ TaskFlow |
| API key / integrations | กุญแจให้โปรแกรมภายนอกเรียกกลุ่มแจ้งเตือน ไม่ใช้แทน session เพื่อแก้รายการงาน |
| Error body / `code` / `message` | ข้อมูลเมื่อผิดพลาด อยู่ใน `{ error: { code, message, request_id } }` โดย code เป็นชื่อให้โปรแกรมแยกกรณี และ message เป็นข้อความอธิบาย |
| `X-Request-ID` | ชื่อ header ที่ส่งหมายเลขคำขอในทุก API response ส่วน error body จะมี `request_id` เพิ่มด้วย ไม่ได้แปลว่าทุก success body มีฟิลด์นี้ |

### คำถามที่อาจถูกถาม

- **ผ่าน Zod แล้วอ่านงานของใครก็ได้หรือไม่?** ไม่ได้ครับ Zod ตรวจรูปแบบข้อมูล ส่วนสิทธิ์ต้องตรวจ credential และ SQL ต้องจำกัด user_id อีกชั้นหนึ่ง
- **จำกัดตาม IP แล้วใช้หลายเครื่องหรือหลาย instance ได้เลยไหม?** ตัวนับปัจจุบันอยู่ใน memory ของ API หนึ่ง instance รีสตาร์ตแล้วเริ่มใหม่ และยังไม่แชร์ตัวนับระหว่างหลาย instance

**ใจความจำ:** รูปแบบข้อมูล ตัวตน และเจ้าของข้อมูลเป็นคนละด่าน ต้องผ่านให้ครบก่อนทำ SQL

## สไลด์ 16: สิทธิ์และสถานะของงาน

ตรงกับไฟล์สไลด์ทดแทนหน้า 11 ใช้แทน PDF เดิมหน้า 14

### บทพูด

ตารางนี้เทียบสิทธิ์เมื่อใช้ credential เพียงชนิดเดียวครับ Session จัดการงานและ key ของตัวเองได้ ส่วน key reminders ใช้อ่านงานถึงกำหนดและบันทึกผลแจ้งเตือนของเจ้าของ key จึงนำไปเพิ่มหรือแก้งานไม่ได้ Session อย่างเดียวก็เข้า integration ไม่ได้ ถ้าส่งทั้งสองชนิด integration ใช้เจ้าของ key เป็นตัวตน ด้านล่างคือ pending ยังไม่เริ่ม in_progress กำลังทำ และ completed เสร็จแล้ว เจ้าของเปลี่ยนสถานะได้โดยไม่บังคับลำดับ การแยกสิทธิ์ช่วยให้โปรแกรมภายนอกทำได้เท่าที่จำเป็น

### คำศัพท์และหน้าที่

| คำที่พบ | ความหมายแบบเข้าใจง่ายและหน้าที่ใน TaskFlow |
|---|---|
| credential | หลักฐานแสดงตัวตนหรือสิทธิ์ ตารางเปรียบเทียบแต่ละชนิดเมื่อใช้เพียงชนิดเดียว |
| Session ผู้ใช้ | สถานะ login ของผู้ใช้เว็บ ใช้จัดการข้อมูลที่เป็นเจ้าของ ไม่ได้ให้สิทธิ์อ่านงานของผู้อื่น |
| API key reminders | คีย์ของบัญชีที่ให้โปรแกรมแจ้งเตือนใช้งาน มี scope สำหรับ reminders เท่านั้น |
| scope | ขอบเขตความสามารถที่คีย์ได้รับ ไม่ใช่สิทธิ์ทุกอย่างของบัญชี |
| Tasks CRUD | สี่การทำงานกับงาน: Create เพิ่ม, Read อ่าน, Update แก้ไข, Delete ลบ ทำได้ผ่าน session ของเจ้าของงาน |
| key / สร้าง key | กุญแจสำหรับเรียก integration ผู้ใช้สร้างและเห็นค่าจริงครั้งเดียว ควรเก็บไว้เป็นความลับ |
| revoke key | ยกเลิกสิทธิ์คีย์ที่ออกแล้ว ทำให้การเรียกครั้งต่อไปด้วยคีย์นั้นถูกปฏิเสธ |
| due-tasks | รายการงานถึงกำหนดตามวันที่ที่เรียกและเข้าเงื่อนไขแจ้งเตือน ต้องเป็นงานของเจ้าของ key |
| reminder | รายการบันทึกว่า workflow ส่งการแจ้งเตือนของงานในวันนั้นผ่านช่องทางที่กำหนดแล้ว API บันทึกผลไม่ได้ส่งอีเมลแทน workflow |
| integration | ช่องทางเชื่อมโปรแกรมภายนอก เช่น n8n กับ API แจ้งเตือน |
| pending | ค่าสถานะในข้อมูล หมายถึงยังไม่เริ่มทำ |
| in_progress | ค่าสถานะหมายถึงกำลังทำ ขีดล่างเป็นส่วนหนึ่งของค่าที่ API รับ |
| completed | ค่าสถานะหมายถึงทำเสร็จแล้ว |

### คำถามที่อาจถูกถาม

- **ถ้าได้ API key มา จะลบงานได้ไหม?** ไม่ได้ครับ route จัดการงานต้องใช้ session คีย์นี้ได้รับสิทธิ์เฉพาะ integration reminders และถูกจำกัดตามเจ้าของคีย์
- **ต้องเปลี่ยน pending ไป in_progress ก่อน completed เสมอไหม?** ไม่บังคับครับ ระบบนี้อนุญาตให้เจ้าของเลือกสถานะที่ถูกต้องได้โดยตรง รวมถึงกลับไปสถานะเดิม

**ใจความจำ:** Session จัดการงานส่วนตัว ส่วน key ให้โปรแกรมแจ้งเตือนทำได้เฉพาะงานที่จำเป็น

## สไลด์ 17: API routes และข้อผิดพลาด

ตรงกับไฟล์สไลด์ทดแทนหน้า 12 ใช้แทน PDF เดิมหน้า 15

### บทพูด

ทุก path หน้านี้ต้องเติม /api ด้านหน้าครับ ต้องอ่าน method คู่กับ path: GET อ่าน POST สร้างหรือสั่งทำงาน PATCH แก้บางส่วน และ DELETE ลบ รายการงานกับงานที่มี id ใช้ method ต่างกัน Reset-password รับ token กับ password ไม่ได้คืน token ใหม่ และไม่ต้องมี session ส่วน error ใช้แยกสาเหตุ เช่น 401 credential ใช้ไม่ได้ 403 Origin ถูกปฏิเสธ และ 429 เรียกถี่เกิน สำหรับ 503 หมายถึงยังไม่ตั้ง SMTP ไม่ใช่ส่งเมลล้มเหลวหลังตอบ 202

### คำศัพท์ โครงสร้าง และทุกเส้นทางที่แสดง

| คำหรือเส้นทางที่พบ | ความหมายและหน้าที่ใน TaskFlow |
|---|---|
| API route | คู่ method กับ path ที่ระบุการทำงานของเซิร์ฟเวอร์ ต้องอ่านคู่กัน |
| method | วิธีเรียก HTTP ที่แยกการกระทำกับข้อมูล |
| path / prefix `/api` | path คือเส้นทางหลังชื่อเว็บ ส่วน prefix คือส่วนที่เติมข้างหน้า เช่น `/auth/login` ในตารางต้องเรียกจริงเป็น `/api/auth/login` |
| GET | ขออ่านข้อมูล ไม่ใช้สร้างหรือแก้รายการงาน |
| POST | ส่งข้อมูลเพื่อสร้างรายการหรือสั่งขั้นตอน เช่น login และ reset ไม่ได้หมายถึงสร้างเสมอไป |
| PATCH | แก้ฟิลด์บางส่วนของรายการที่มีอยู่ ไม่ต้องส่งทุกฟิลด์ |
| DELETE | ลบงาน หรือยกเลิก API key ตาม route ที่เรียก |
| `POST /auth/register` | สมัครบัญชีด้วยข้อมูลที่ผ่าน validation สำเร็จตอบ 201 |
| `POST /auth/login` | ตรวจอีเมลและรหัสผ่าน แล้วสร้าง session สำเร็จตอบ 200 |
| สาธารณะ | ไม่ต้องมี session หรือ API key เดิม แต่ยังตรวจข้อมูล Origin และข้อจำกัดการเรียก |
| `POST /auth/forgot-password` | รับ `{ email }` เพื่อขอส่งลิงก์ ตอบข้อความทั่วไปแบบ 202 เพื่อลดการเปิดเผยว่าบัญชีมีอยู่หรือไม่ |
| `email` | ฟิลด์อีเมลบัญชีที่ต้องการขอลิงก์ ไม่ใช่ SMTP_USER ของผู้ส่ง |
| 202 Accepted | รับคำขอแล้ว งานส่งเมลจะทำต่อแบบ async ยังไม่รับรองว่าส่งเสร็จหรือถึงผู้รับ |
| `POST /auth/reset-password` | รับ `{ token, password }` เพื่อยืนยันสิทธิ์และตั้งรหัสใหม่ สำเร็จตอบ 200 ไม่ต้องส่ง email รหัสเดิม หรือ confirmation ไป API |
| `token` / `password` | ฟิลด์หลักฐานจากลิงก์และรหัสใหม่ตามลำดับ เป็นข้อมูลรับเข้า route reset ไม่ใช่ response token ใหม่ |
| `GET /tasks` / `POST /tasks` | อ่านรายการงานของตนเอง / เพิ่มงานใหม่ ต้องใช้ session |
| `GET /tasks/:id` | อ่านงานหนึ่งรายการตาม id โดยต้องเป็นเจ้าของ |
| `PATCH /tasks/:id` | แก้บางส่วนของงานหนึ่งรายการโดยต้องเป็นเจ้าของ |
| `DELETE /tasks/:id` | ลบงานหนึ่งรายการโดยต้องเป็นเจ้าของ ทั้งสาม method นี้ไม่ได้ใช้กับ collection ทุกกรณี |
| `:id` | ตำแหน่งแทนรหัสรายการจริงใน URL เช่น `/tasks/7` ไม่ได้ส่งอักษร `:id` ตรง ๆ |
| `GET /keys` / `POST /keys` | อ่านรายการ key ของตน / สร้าง key ใหม่ ใช้ session |
| `DELETE /keys/:id` | ยกเลิก key ตาม id ของตน ใช้ session ไม่ได้หมายถึงมี DELETE `/keys` แบบลบทั้งหมด |
| `GET /integrations/due-tasks` | อ่านงานถึงกำหนดสำหรับ workflow ใช้ API key scope reminders |
| `POST /integrations/reminders` | บันทึกผลแจ้งเตือน รับ `{ task_ids, date, channel: 'email' }` ใช้ API key ไม่ใช่ endpoint ส่งเมล |
| `task_ids` / `date` / `channel` | รายการ id งาน / วันแจ้งเตือนรูปแบบ YYYY-MM-DD / ช่องทาง ซึ่งขณะนี้รองรับค่า `email` |
| Session ผู้ใช้ / API key scope reminders | หลักฐานคนละชนิด ใช้ตามเส้นทาง ไม่สลับแทนกันได้ทุก route |
| Error body | ตัวข้อมูลตอบเมื่อผิดพลาด อยู่ใน `{ error: { code, message, request_id } }` success มีโครงสร้างตาม route ไม่ได้ห่อ error |
| `code` / `message` / `request_id` | ชื่อเหตุผิดพลาดให้โปรแกรมใช้แยกกรณี / ข้อความที่อ่านได้ / หมายเลขอ้างอิงคำขอ |

### รหัสตอบกลับทุกตัวในตาราง

| รหัสหรือคำ | ความหมายและขอบเขต |
|---|---|
| 400 | ข้อมูล JSON, schema, filter หรือวันที่ไม่ถูกต้อง; reset token ที่รูปแบบผ่านแต่ไม่พบ หมดอายุ หรือใช้แล้วเป็น `INVALID_RESET_TOKEN` ถ้ารูปแบบ token ผิดจะเป็น `VALIDATION_ERROR` |
| 401 | ไม่มี credential หรือ session, JWT, API key ใช้ไม่ได้ |
| 403 / Origin | ต้นทางคำขอแก้ข้อมูลไม่ถูกยอมรับ ไม่ใช่รหัสสำหรับทุกกรณีที่งานเป็นของผู้อื่น |
| 404 | ไม่พบรายการหรือรายการนั้นไม่ใช่ของผู้เรียก ใช้ข้อความลักษณะเดียวกัน |
| 409 | ข้อมูลขัดแย้ง เช่นอีเมลซ้ำ หรือจำนวน active key ถึงขีดจำกัด 5 อัน |
| 413 / Body / 16KB | ข้อมูลตัวคำขอใหญ่เกิน 16,384 ไบต์ตามขอบเขตของโครงการนี้ |
| 415 / Content-Type / JSON | ตัวคำขอที่ต้องรับ JSON ไม่ได้ระบุชนิดเป็น `application/json`; route ไม่มี body อย่าง DELETE และ logout ไม่ต้องส่ง body เพื่อให้ผ่านเงื่อนไขนี้ |
| 429 / rate limit | เรียกเกินจำนวนที่อนุญาต ดู header `Retry-After` ว่าควรรออีกเท่าใด |
| 500 | ข้อผิดพลาดภายใน คืนข้อความทั่วไป ไม่เปิดเผย stack หรือคำสั่ง SQL ให้ผู้ใช้ |
| 503 / SMTP | การขอ reset ยังใช้ไม่ได้เพราะตั้งค่า SMTP ไม่ครบ ใช้ชื่อ `SMTP_NOT_CONFIGURED` ไม่ได้ใช้บอกผลส่งเมลล้มเหลวภายหลัง 202 |

### คำถามที่อาจถูกถาม

- **ทำไมงานคนอื่นตอบ 404 แทน 403?** เพื่อไม่ยืนยันให้ผู้เรียกรู้ว่างาน id นั้นมีอยู่จริงครับ ส่วน 403 ที่ยกตัวอย่างหน้านี้ใช้กับการตรวจ Origin
- **reset-password ตอบ token กลับให้หรือไม่?** ไม่ครับ token ต้องส่งเข้ามาจากลิงก์พร้อมรหัสใหม่ ถ้าสำเร็จตอบว่าสำเร็จแล้วให้ login ใหม่ ไม่มีการออก session อัตโนมัติ

**ใจความจำ:** อ่าน method คู่กับ path เลือก credential ให้ถูก และใช้รหัส error อธิบายสาเหตุให้ตรง

### คำถามที่อาจถูกถาม

- **รับประกันว่าแต่ละงานส่งเมลครั้งเดียวหรือไม่?** ไม่รับประกันครับ บันทึกผลช่วยลดการซ้ำ แต่มีช่องระหว่างส่ง SMTP กับบันทึก SQL และถ้ารันสองชุดพร้อมกันก็อาจส่งซ้ำได้
- **SMTP ใน backend ตั้งแล้ว n8n ใช้ได้เองไหม?** ไม่ครับ เป็นคนละการตั้งค่า ต้องตั้ง API key และ SMTP credentials ใน n8n เอง โดยยังไม่ใช้ session ผู้ใช้เว็บ

**ใจความจำ:** n8n อ่านงาน ส่งเมล แล้วบันทึกผล แต่ยังต้องทดสอบรันจริงและระวังช่วงที่อาจส่งซ้ำ

| Database schema กับ shared schema | Database schema กำหนดตารางและข้อบังคับใน SQL ส่วน shared schema กำหนดกติกาข้อมูลที่เว็บและ API ใช้ร่วมกันผ่าน Zod |
| SMTP สำหรับ reset กับ SMTP ใน n8n | Reset ส่งจาก backend ส่วน n8n ส่งอีเมลเตือนงานตามเวลา ใช้ค่าตั้ง SMTP แยกกัน ตั้งฝั่งหนึ่งไม่ได้ตั้งอีกฝั่งให้อัตโนมัติ |
| รับคำขอ กับส่งเมล กับเข้า inbox | 202 คือรับคำขอ SMTP ยอมรับคือเซิร์ฟเวอร์เมลรับข้อความไปส่งต่อ ส่วนเข้า inbox ต้องตรวจปลายทาง แต่ละขั้นเป็นหลักฐานคนละอย่าง |
| SQL transaction กับการส่งอีเมล | Transaction ย้อนการเปลี่ยนข้อมูลภายใน SQL ได้ แต่ดึงอีเมลที่ส่งออกไปแล้วกลับคืนไม่ได้ การส่ง SMTP กับบันทึกประวัติจึงไม่ได้สำเร็จพร้อมกันโดยอัตโนมัติ |

## จุดชี้โค้ดเมื่อถูกถามต่อ

| เรื่อง | ไฟล์และสิ่งที่ให้ชี้ |
| --- | --- |
| กติกาข้อมูลร่วมกัน | `packages/shared/src/index.ts` ดู `taskSchema`, `taskUpdateSchema`, `resetPasswordSchema` |
| ตรวจว่าเป็นเจ้าของงาน | `apps/api/src/tasks.ts` ดู `WHERE id = ? AND user_id = ?` |
| การออกและตรวจ JWT | `apps/api/src/security.ts` ดู `issueToken` และ `verifyToken` |
| ยกเลิก session | `apps/api/src/auth.ts` ดู `sessionMiddleware` และ route `/logout` |
| Reset ใช้ครั้งเดียว | `apps/api/src/password-reset.ts` ดู conditional UPDATE และตรวจ `claimed.changes !== 1` ภายใน transaction |
| ข้อผิดพลาดและ rate limit | `apps/api/src/app.ts` ดู middleware, `rateLimit` และ `onError` |
| ตารางและความสัมพันธ์ | `apps/api/src/schema.sql` ดู PRIMARY KEY, REFERENCES และ UNIQUE |
| การส่งอีเมล reset | `apps/api/src/mail.ts` และ `password-reset.ts` ส่วนเรียก `mail.send` |
| Workflow แจ้งเตือน | `n8n/taskflow-daily-reminder.json` และ `apps/api/src/integrations.ts` |

## แหล่งที่ใช้ตรวจคำอธิบาย

พฤติกรรมและตัวเลขของ TaskFlow อิงโค้ดในโครงการ ไม่ได้อ้างว่าค่าตั้งเหล่านี้เป็นข้อบังคับของ JWT หรือทุกระบบ

- [JWT และความหมายของ claims: RFC 7519](https://datatracker.ietf.org/doc/html/rfc7519) ใช้ประกอบความหมายของ JWT, sub, exp, iss และ aud
- [npm workspaces](https://docs.npmjs.com/cli/v11/using-npm/workspaces/) ใช้ประกอบหน้าที่ของ package ภายในโครงการ
- [Google App Passwords](https://support.google.com/accounts/answer/185833?hl=en) ใช้ตรวจเงื่อนไขบัญชี Google สำหรับการเชื่อม SMTP
- [n8n Schedule Trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.scheduletrigger) ใช้ประกอบการตั้งเวลาและ timezone ของ workflow
