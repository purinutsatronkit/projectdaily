# TaskFlow: สคริปต์ซ้อมพูดตามสไลด์ของคุณ 14 หน้า

เรียงตาม PDF ฉบับล่าสุด 14 หน้า ใช้สำนวนผู้ชาย ย่อหน้าภายใต้แต่ละหัวข้อคือบทพูดจริง เว้นจังหวะชี้ภาพหรือตารางตามที่กำลังอธิบาย

ก่อนนำเสนอ ให้แก้ข้อความบนสไลด์หน้า 4, 5 และ 10 ตามข้อเสนอแนะรอบก่อน บทพูดนี้ใช้โครงสร้างโค้ดจริง ไม่พูดตามข้อความเดิมที่ยังคลาดเคลื่อน

## หน้า 1: TaskFlow ระบบจัดการงานส่วนตัว

สวัสดีครับ วันนี้ผมจะนำเสนอ TaskFlow เป็นเว็บจัดการงานส่วนตัว ผู้ใช้เพิ่มงาน กำหนดวันส่ง และติดตามสถานะได้ หน้าจอใช้ React ร่วมกับ Tailwind ส่วน backend ใช้ Hono รับคำขอ และใช้ SQLite เก็บข้อมูล จุดที่ผมจะอธิบายคือการแบ่ง frontend กับ backend การใช้กติกาข้อมูลร่วมกัน และการตรวจสิทธิ์ของผู้เรียก เว็บใช้ JWT ร่วมกับ session ส่วน n8n ใช้ API key สำหรับแจ้งเตือน นอกจากนี้มีระบบลืมรหัสผ่านผ่านลิงก์อีเมล โดยทุกส่วนยังจำกัดให้ผู้ใช้จัดการได้เฉพาะข้อมูลของตัวเองครับ

## หน้า 2: หน้าจอและเส้นทางการใช้งาน

หน้านี้เป็นภาพ TaskFlow ที่รันจริงครับ ด้านบนสรุปจำนวนงานตามสถานะ ด้านล่างค้นหา กรอง เพิ่ม และแก้ไขงานได้ ผู้ใช้เลือกความสำคัญและวันครบกำหนดของแต่ละงานได้ด้วย ระบบนำแนวคิดจากบทเรียนสองเรื่องมาใช้ เรื่องแรกคือ API และการยืนยันตัวตน โดย Hono รับคำขอและผ่านขั้นตรวจที่เรียกว่า middleware ก่อนทำงาน ส่วนรหัสผ่านเก็บเป็น scrypt hash ร่วมกับ salt เรื่องที่สองคือ monorepo ซึ่งรวมเว็บ API และกติกาข้อมูลไว้ใน repository เดียว เพื่อให้สองฝั่งใช้กติกาที่ตรงกันครับ

## หน้า 3: สถาปัตยกรรมของ TaskFlow

ให้อ่านภาพจาก Browser ไป Hono API แล้วไป SQLite ครับ Browser แสดงหน้าจอและส่งข้อมูลแบบ JSON ผ่าน HTTP ส่วน Node.js รัน backend และ Hono เลือกโค้ดที่จะจัดการคำขอ ฐานข้อมูลเก็บบัญชี งาน session API key reset token และประวัติแจ้งเตือน ตอนพัฒนา Vite เปิดเว็บพอร์ต 5173 และ Hono เปิด API พอร์ต 3000 หลัง build สามารถให้ Hono เสิร์ฟทั้งเว็บและ API จากที่อยู่เดียวกันได้ ด้านล่าง n8n เป็นผู้เรียก Hono ด้วย API key ส่วนลิงก์ตั้งรหัสผ่านใหม่ส่งจาก backend ผ่าน SMTP โดยตรงครับ

## หน้า 4: Monorepo และ package ที่แชร์ร่วมกัน

Monorepo หมายถึงเก็บหลายแอปหรือ package ที่เกี่ยวข้องไว้ใน repository เดียวครับ โฟลเดอร์ apps/web เป็น frontend ส่วน apps/api เป็น backend และ packages/shared เก็บ Zod schema กับชนิดข้อมูลที่สองฝั่งใช้ร่วมกัน ส่วน workflow อยู่ใน n8n และคู่มืออยู่ใน docs ฝั่งขวาแสดงว่าเว็บกับ API เรียกใช้ shared ตัวเดียวกัน npm workspaces ช่วยเชื่อม package ภายใน จึงไม่ต้องคัดลอกกติกาไปไว้สองที่ ส่วนการรันเว็บกับ API พร้อมกัน เกิดจาก root script ที่ใช้ concurrently ไม่ใช่คุณสมบัติที่ monorepo ทำให้เองครับ

## หน้า 5: Shared schema และการตรวจข้อมูล

Shared schema คือกติกาข้อมูลชุดเดียวที่เว็บกับ API ใช้ร่วมกันครับ เช่น ชื่องานต้องยาวเท่าไร สถานะรับค่าอะไร และวันที่ต้องมีอยู่จริง หน้าเว็บตรวจเพื่อแจ้งผู้ใช้ทันที แต่ backend ต้องตรวจซ้ำ เพราะผู้เรียกส่งคำขอเข้าตรงโดยไม่ผ่านฟอร์มได้ เราใช้ Zod ตรวจค่าจริงตอนโปรแกรมทำงาน ส่วน TypeScript ช่วยตรวจโค้ดก่อนรัน ถ้า PATCH ส่งสถานะผิด API จะตอบ 400 และไม่เขียนข้อมูลงาน ส่วนช่องที่ไม่ได้ส่งมาต้องคงค่าเดิม คำว่าไม่เขียนงานนี้แยกจากการอ่าน SQL เพื่อตรวจ session ซึ่งอาจเกิดก่อนหน้านั้นครับ

## หน้า 6: JWT, cookie และการเพิกถอน session

เมื่อ login สำเร็จ ระบบส่ง JWT ให้ Browser เก็บใน cookie ครับ ข้อมูลข้างในอ่านได้ จึงไม่ใส่รหัสผ่าน sub คือรหัสผู้ใช้ sid คือรหัส session และ exp คือเวลาหมดอายุ Backend ตรวจลายเซ็นด้วย HS256 ซึ่งใช้กุญแจลับเดียวกันตอนสร้างและตรวจ พร้อมตรวจ iss ว่าใครออก token และ aud ว่าออกให้ระบบใดใช้ จากนั้นยังต้องตรวจ session ใน SQL ว่าไม่หมดอายุและไม่ถูกยกเลิก ตอน logout ระบบตั้ง revoked_at และลบ cookie สำเนา JWT เดิมจึงใช้ต่อไม่ได้ อายุ JWT และ session คือ 30 นาที ไม่มี refresh token จึงต้อง login ใหม่เมื่อหมดอายุครับ

## หน้า 7: เปรียบเทียบ JWT, API key และ reset token

ตารางนี้แยกหลักฐานสามชนิดตามหน้าที่ครับ JWT ร่วมกับ SQL session ใช้กับผู้ใช้เว็บ อายุ 30 นาที API key ส่งใน header ชื่อ x-api-key ใช้กับ n8n สำหรับแจ้งเตือน อายุ 30 วัน ส่วน reset token ใช้ตั้งรหัสผ่านใหม่ อายุ 15 นาทีและใช้สำเร็จได้ครั้งเดียว API key กับ reset token เก็บเป็น SHA-256 digest ซึ่งคือผลแฮช แทนการเก็บค่าลับดิบ ส่วนรหัสผ่านใช้ scrypt ร่วมกับ salt เพื่อเพิ่มต้นทุนการเดาและทำให้รหัสเดียวกันได้แฮชต่างกัน JWT อยู่ใน HttpOnly cookie จึงอ่านค่าจาก JavaScript โดยตรงไม่ได้ และการ reset รหัสผ่านไม่ได้ยกเลิก API key อัตโนมัติครับ

## หน้า 8: Token ใช้ครั้งเดียวและ transaction

Reset token สุ่มจากข้อมูล 32 ไบต์ แล้วเก็บเฉพาะผล SHA-256 ครับ เมื่อตั้งรหัสใหม่ ระบบคำนวณ scrypt hash ก่อนเปิด transaction จากนั้น claim token ด้วยการอัปเดตที่มีเงื่อนไขว่ายังไม่ใช้และไม่หมดอายุ พร้อมตรวจว่าอัปเดตได้หนึ่งแถวจริง จึงบันทึก password hash ยกเลิกทุก session และปิดลิงก์ reset ที่ค้างของบัญชีนั้น Transaction ทำให้ทุกขั้นสำเร็จด้วยกัน หรือ rollback ย้อนกลับทั้งชุด ถ้าสองคำขอใช้ token เดียวพร้อมกันจึงสำเร็จได้เพียงคำขอเดียว ส่วน login ที่ทำงานซ้อนกับ reset ต้องอ่าน hash ปัจจุบันก่อนออก session เพื่อไม่ยอมรับผลตรวจจากรหัสเก่าครับ

## หน้า 9: หน้าตั้งรหัสผ่านใหม่ที่ใช้งาน

หน้านี้เป็นฟอร์มตั้งรหัสผ่านใหม่ครับ ผู้ใช้กรอกรหัสยาว 12 ถึง 128 ตัวอักษร และยืนยันให้ตรงกัน เมื่อเปิดลิงก์ หน้าเว็บอ่าน token จาก fragment ซึ่งคือส่วนหลังเครื่องหมายชาร์ป เข้า memory แล้วลบ fragment จากแถบที่อยู่ทันที เพื่อลดการทิ้งค่าลับไว้ใน URL Token ไม่ได้เก็บให้คงอยู่หลังโหลดหน้าใหม่ ถ้า refresh จึงต้องเปิดลิงก์ต้นฉบับจากอีเมลอีกครั้ง โดยลิงก์ต้องยังไม่หมดอายุและไม่ถูกใช้ เมื่อบันทึกสำเร็จ ระบบยกเลิก session เดิมของบัญชีทั้งหมด แล้วให้ผู้ใช้ login ใหม่ด้วยรหัสที่ตั้งครับ

## หน้า 10: การตั้ง Gmail SMTP และขอบเขตหลักฐาน

Backend ส่งอีเมลผ่าน SMTP ซึ่งเป็นกติกาส่งอีเมลระหว่างโปรแกรมกับเซิร์ฟเวอร์เมลครับ เริ่มจาก npm run setup:email แล้วตั้งบัญชีผู้ส่งกับ Gmail App Password ใน .env และกำหนด APP_PUBLIC_URL ให้ผู้รับเปิดถึง คำสั่ง mail:check ตรวจการเชื่อมต่อและยืนยันตัวตน แต่ไม่ส่งอีเมล การส่งจริงทำแบบ async คือรับคำขอแล้วส่งต่อภายหลังใน process เดิม ยังไม่มีคิวถาวร หลักฐานที่มีคือส่งถึงตัวรับ SMTP ในเครื่อง ยังไม่ยืนยัน Gmail ถึง inbox และ SMTP ยอมรับข้อความไม่ได้แปลว่าเข้า inbox แล้ว ลิงก์อายุ 15 นาที ต่อบัญชีเว้น 60 วินาที และสร้างได้ 3 token ในช่วงหนึ่งชั่วโมงย้อนหลังครับ

## หน้า 11: การตรวจ request ก่อนแตะข้อมูล

คำขอหนึ่งครั้งต้องผ่านหลายด่านครับ เริ่มจาก request_id ซึ่งเป็นหมายเลขติดตามคำขอ และ secure headers ที่กำหนดกติกาด้านความปลอดภัยให้ Browser จากนั้นจำกัด body ไม่เกิน 16 KB และตรวจ Origin ของคำขอแก้ข้อมูล ต่อมาจึงตรวจ credential หรือหลักฐานตาม route งานส่วนตัวใช้ session ส่วน integration ใช้ API key แล้วตรวจ JSON กับ Zod ก่อนดำเนินการกับข้อมูลงาน ซึ่งยังต้องตรวจเจ้าของด้วย Login กับ register ใช้ตัวนับรวม 20 ครั้งต่อ IP ใน 15 นาที ส่วน forgot-password 5 และ reset-password 10 ครั้ง ถ้าผิดพลาดจะคืน code ข้อความ และ request_id เพื่อค้นหาปัญหาครับ

## หน้า 12: สิทธิ์และสถานะของงาน

ตารางนี้แสดงว่าหลักฐานแต่ละชนิดให้ทำอะไรได้ครับ Session ผู้ใช้จัดการงานและ API key ของตัวเองได้ ส่วน API key reminders อ่านงานถึงกำหนดและบันทึกผลแจ้งเตือนของเจ้าของ key แต่เพิ่ม แก้ หรือลบงานไม่ได้ Session อย่างเดียวก็เข้า integration ไม่ได้เช่นกัน ตอนอ่าน แก้ หรือลบงานหนึ่งรายการ backend ตรวจทั้งรหัสงานและ user_id จาก session ส่วนการอ่านรายการกรองตาม user_id จึงไม่ให้เข้าถึงงานของบัญชีอื่น ด้านขวาคือ pending ยังไม่เริ่ม in_progress กำลังทำ และ completed เสร็จแล้ว เจ้าของเปลี่ยนสถานะกลับได้ ไม่ได้บังคับให้เดินหน้าอย่างเดียวครับ

## หน้า 13: API routes และข้อผิดพลาด

เวลาอ่านตารางนี้ต้องดู method คู่กับ path และเติม /api ด้านหน้าครับ GET ใช้อ่าน POST ใช้สร้างหรือสั่งทำงาน PATCH แก้บางส่วน และ DELETE ลบ งานกับ key ต้องใช้ session ส่วน integration ต้องใช้ API key สำหรับ reset-password ต้องส่ง token พร้อม password ใหม่ ไม่ได้ขอ token กลับมา ส่วน forgot-password ตอบ 202 หมายถึงรับคำขอไว้ ยังไม่ยืนยันว่าเมลถึง รหัสสถานะ HTTP อื่นช่วยแยกสาเหตุ เช่น 400 ข้อมูลผิด 401 หลักฐานใช้ไม่ได้ 404 ไม่พบหรือไม่ใช่เจ้าของ 429 เรียกเกินจำนวน และ 503 ยังไม่ตั้ง SMTP ครับ

## หน้า 14: n8n workflow แจ้งเตือนรายวัน

Workflow นี้เริ่มเวลาเจ็ดโมงครึ่งตามเวลา Bangkok ครับ Schedule เป็นตัวเริ่ม แล้วใช้ API key เรียกงานที่ยังไม่เสร็จและถึงกำหนด IF ตรวจว่ามีงานหรือไม่ ถ้ามีจึงส่งอีเมลผ่าน SMTP แล้วเรียก API บันทึก delivery หรือประวัติแจ้งเตือน แต่ละ workflow ใช้ key ของบัญชีเดียว และตั้งข้อมูล SMTP แยกจาก backend การบันทึกช่วยลดการส่งซ้ำ แต่ SMTP กับ SQL ไม่ใช่ transaction เดียวกัน ถ้าส่งแล้วหยุดก่อนบันทึกก็อาจส่งซ้ำได้ ตอนนี้ผ่าน static validation ซึ่งตรวจไฟล์และ expression ยังไม่ได้รัน n8n ส่งอีเมลจริงครับ

## ประโยคปิด

หัวใจของระบบนี้คือให้ frontend รับข้อมูล แล้วให้ backend ตรวจข้อมูลและสิทธิ์ก่อนจัดการงาน โดยแยก session ผู้ใช้ API key และ reset token ตามหน้าที่ครับ ขอบคุณครับ
